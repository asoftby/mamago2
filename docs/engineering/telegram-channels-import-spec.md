# ТЗ: Автосбор событий из Telegram-каналов в афишу mamaGo

Дата: 2026-10-29 · Владелец: Алексей · Статус: утверждено к реализации

## Цель и границы

Каждый публичный Telegram-канал становится ещё одним источником существующего импорта (`ImportSource` + новый парсер). Система по расписанию читает каналы, распознаёт текст и изображения постов общим с Capture мультимодальным модулем и кладёт события в существующую очередь ревью `/admin/import/review`. На сайте без решения редактора не появляется ничего.

**В скоупе:**

- Общий мультимодальный модуль, выделенный из Telegram Capture без изменения поведения личного плана.
- Парсер `telegram-channel-event`: чтение публичного канала через веб-версию `t.me/s/<канал>`.
- Нормализатор постов на общем модуле: текст и изображения, анонс / фестиваль / подборка / не событие, источник каждого значения и противоречия.
- Доработка существующего матчера событий: дубли между каналами, ABWS (24afisha) и family.by, в том числе среди ещё не разобранных записей.
- Плановые запуски импорта в существующем worker (сейчас импорт запускается только вручную).
- Доработки очереди ревью под Telegram: ссылка на пост, противоречия, пакетные действия, фильтры.

**Вне скоупа:**

- Telegram-группы через Bot API — следующий этап, после пилота на каналах.
- Автоматическая публикация и автоматическое слияние событий: решение всегда принимает редактор.
- Приватные каналы и чтение через отдельный Telegram-аккаунт (MTProto).
- Редакторский бот для пересылки постов: отдельная задача, позже подключается к тому же нормализатору.
- Изменение кода парсеров family.by и ABWS.
- Новые параллельные сущности: используются только `ImportSource`, `ImportedRecord`, `ImportReviewTask` и существующий матчер.

## Этапы и порядок работ

Работа идёт тремя этапами; следующий начинается только после проверки предыдущего на DEV.

1. **Общий мультимодальный модуль.** Из Capture выносятся загрузка изображений, вызов модели, повтор и эскалация на сильную модель, учёт токенов. Пользовательское поведение Capture не меняется. Переход дальше — после зелёного CI, merge в `dev` и ручной проверки Capture на DEV: пересланный текст, скриншот, альбом, сообщение с двумя датами, событие с несколькими сеансами.
2. **Импорт Telegram-каналов** (текущий релиз). `t.me/s` → существующий Import Pipeline → нормализатор на общем модуле → матчер → ревью. Пилот на 2–3 каналах.
3. **Telegram-группы** (не в текущем релизе). Bot API, новые сообщения через webhook, отдельный `ImportSource` на группу, только группы организаторов с согласия админов.

**Метрики пилота** на первых 100 постах каждого канала: ложные события, пропущенные анонсы, ошибки дат, найденные и пропущенные дубли, доля правок редактора, стоимость модели на 100 постов. По ним решаем о подключении следующих каналов.

**Найденные проблемы:**

- **Импорт только ручной.** `isAutoUpdate` хранится, но ничего его не читает. `ImportTriggerType.SCHEDULED` есть в схеме, но `runImportForSource` всегда пишет `MANUAL` (`triggeredByUserId ? "MANUAL" : "MANUAL"`).
- **Дубли между источниками до публикации не ищутся.** Кандидаты берутся только из `Activity`. Если пост из канала и запись ABWS о том же событии оба ждут ревью, матчер их не свяжет.
- **Поиск кандидатов слабый.** Берётся первое слово названия (`contains`) или первое слово площадки, не больше `CANDIDATE_LIMIT`. Дата сравнивается только с `nextOccurrenceAt`, без сеансов и без времени суток.
- **Баг нормализации адреса.** В `normalizeAddress` регулярка `\b(ул|улица|пр|…)\b` не срабатывает на кириллице: `\b` в JS работает только для латиницы. Проверено: `"ул ленина"` остаётся без изменений. Совпадение адресов из-за этого занижено для всех источников.
- **Ревью-задача создаётся для каждой записи.** Для Telegram это значит, что каждый пост (реклама, опрос, подборка) попадает в очередь. Нужен автоотсев с закрытием задачи.
- **Нет `pg_trgm`**, похожесть считается `tokenJaccard`. Расширение не добавляем, остаёмся на текущем подходе.

**Что из ТЗ от 26.10 отменяется:** модели `EventSource`, `IngestDraft`, `MatchDecision`, `Channel`, `ChannelPost` и `pg_trgm` не создаются. Их роль выполняют `ImportSource`, `ImportedRecord`, `ImportReviewTask` и `reviewDecision`.

**Дополнение аудита: Telegram Capture.** В первой версии аудита Capture учтён только как источник правил промпта. На деле это готовый мультимодальный конвейер: `captureProcessor.ts` скачивает фото через `getFile`/`downloadFile`, передаёт их моделью как data URL, повторяет запрос, эскалирует на сильную модель и считает токены. Capture принимает только личные чаты (`NOT_PRIVATE_CHAT` в `telegramUpdateParser.ts`) и пользователей из allowlist; лимиты `CAPTURE_LIMITS`: 5 фото до 5 МБ, склейка альбома 2,5 с, 30 сообщений в сутки, очистка через 7 дней. Эти механизмы выносятся в общий модуль, лимиты — нет.

## Общий мультимодальный модуль

Загрузка изображений, вызов модели и обработка ошибок выносятся из Capture в `src/server/ai/extraction/`; Capture и импорт каналов вызывают один модуль со своими промптами, схемами и лимитами.

**Что выносится из `captureProcessor.ts` без изменения поведения:**

- загрузка изображений (`loadImages`) — за интерфейсом адаптера;
- вызов OpenRouter со структурированным ответом (`json_schema` / `json_object`);
- политика попыток: быстрая модель, один повтор, эскалация на сильную модель при невалидном ответе или `OPENROUTER_BAD_RESPONSE`;
- учёт модели и токенов (`usage`) и коды ошибок.

Промпт `CAPTURE_SYSTEM_PROMPT`, схема `CaptureDraft`, `applyPostLlmRules`, контекст семьи и `CAPTURE_LIMITS` остаются в Capture.

**Два адаптера получения изображений, один формат на выходе:**

| Адаптер | Вход | Где используется |
| --- | --- | --- |
| `TelegramFileImageSource` | `file_id` → `getFile` + `downloadFile` | Capture сейчас, группы на этапе 3 |
| `WebImageSource` | URL картинки → `fetchBinary` с SSRF-защитой и allowlist хостов (`*.telesco.pe`, `t.me`) | Каналы через `t.me/s` |

Оба возвращают `LoadedImage { bytes, mime, sha256, width?, height?, origin }`. После загрузки изображения идут в один механизм распознавания: проверка размера и формата, уменьшение под лимит модели, data URL.

**Профили лимитов** передаются вызывающим кодом, а не зашиты в модуль:

| Параметр | Capture (как сейчас) | Импорт каналов |
| --- | --- | --- |
| Фото в одном вызове | 5 | 10 (весь альбом) |
| Размер фото | 5 МБ | 5 МБ, крупнее — уменьшается перед отправкой |
| Квота | 30 сообщений на пользователя в сутки | Бюджет на запуск источника, например 60 вызовов модели |

**Идентификация изображений по содержимому.** CDN-ссылки Telegram меняются, поэтому изображение определяется по `sha256` байтов, а не по URL. Парсер канала скачивает только URL, которых ещё нет у записи этого поста; для известных URL берёт сохранённый `sha256`.

**Источник каждого значения.** Общий формат результата хранит для ключевых полей (дата, время, место, цена, возраст, регистрация) значение, состояние `stated` / `inferred` / `missing` и происхождение: `TEXT`, `IMAGE` с индексом картинки или `BOTH`. Если текст и картинка дают разные значения, сохраняются оба вместе с флагом `conflict`; модель не выбирает одно молча.

**Регресс Capture.** Существующие тесты (`captureProcessor.integration.test.ts`, `capturePureFunctions.test.ts`, `captureRules.test.ts` и другие) проходят без изменения ожиданий. Новые тесты — на сам модуль: оба адаптера, повтор, эскалация, ошибка загрузки файла.

## Архитектура

Telegram подключается как ещё один парсер к существующему `runImportForSource`; новых сервисов-оркестраторов, таблиц очередей и экранов модерации не создаём.

1. **Worker** раз в 15 минут находит источники с `isAutoUpdate = true`, `status = ACTIVE`, у которых подошёл интервал, и вызывает `runImportForSource(sourceId)` с `triggerType = SCHEDULED`.
2. **Парсер `telegram-channel-event`** читает последние страницы `t.me/s/<канал>` и отдаёт по записи на пост (`externalId = <канал>/<messageId>`).
3. **Пайплайн** сохраняет записи; пост с тем же `contentHash` пропускается без вызова модели.
4. **Нормализатор Telegram** (LLM) на общем мультимодальном модуле читает текст и изображения поста, классифицирует его и превращает анонс в `NormalizedEventImport`; подборку раскладывает на дочерние записи; не-события и прошедшие события закрывает со статусом `SKIPPED`.
5. **Матчер** (доработанный) ищет дубли среди опубликованных событий и среди ожидающих записей других источников.
6. **Очередь ревью** `/admin/import/review`: редактор публикует, дополняет существующее или отклоняет. Публикация создаёт событие со статусом `PENDING`, как сейчас.
7. **Сводка** раз в день уходит в админский Telegram: пришло, дубли, ждёт решения.

**Настройка канала** — обычная форма источника: `type = TELEGRAM_CHANNEL`, `parserKey = telegram-channel-event`, `baseUrl = https://t.me/s/minsk_kids`, `territoryId` (подсказка городу), `crawlMaxPages`, `rateLimitMs`, интервал запуска, `isAutoUpdate`. Проверка нового канала — существующий dry-run «Тест источника».

## Чтение канала

Канал читается через публичную веб-версию `t.me/s/<канал>`: без аккаунта и токенов, только публичные каналы. Bot API не подходит — бот видит посты только каналов, где он администратор.

- **Окно чтения.** Каждый запуск читает первую страницу и листает назад через `?before=<минимальный id>` до `crawlMaxPages` (по умолчанию 3, это около 60 постов) или до постов старше 14 дней. Курсор не храним: неизменённые посты отсекаются по `contentHash`, а правки постов в окне ловятся автоматически.
- **Первый запуск** нового канала: `crawlMaxPages = 5`, посты старше 30 дней пропускаются.
- **Что извлекаем из поста:** id и дату (`data-post`, `<time datetime>`), текст с переносами строк, ссылки из `<a href>` вместе с их текстом («Билеты», «в директ», адрес со ссылкой на Яндекс.Карты), хэштеги, фото альбома (URL с CDN Telegram), признаки `опрос`, `пересланный из` и `реклама`.
- **Альбом** на `t.me/s` уже отдаётся одним постом с несколькими фото — склейка не нужна.
- **Безопасность:** загрузка только через `fetchHtml` с хуком, разрешающим хосты `t.me` и `telesco.pe`/`cdn*.telesco.pe` (картинки). Имя канала валидируется регуляркой `^[A-Za-z0-9_]{5,32}$`.
- **Нагрузка:** пауза между страницами из `rateLimitMs` (по умолчанию 1500 мс), каналы запускаются последовательно, не параллельно.
- **Ошибки:** HTTP-ошибка или пустая страница помечают запуск `FAILED` через существующие `lastErrorAt`/`lastErrorMessage`. После 5 неудачных запусков подряд worker переводит источник в `status = ERROR` и шлёт уведомление.
- **Удалённый пост** события не снимает: запись просто перестаёт обновляться.
- **Фикстуры для тестов:** сохранённый HTML `t.me/s/minsk_kids` с постом `3743` (альбом из 7 фото, фестиваль) и постом `3729` (подборка из двух фильмов).

**Контроль расходов: сначала хэш, потом модель.**

1. Парсер для каждого поста собирает стабильное содержимое: текст, ссылки с их текстом, хэштеги, признаки поста и список `sha256` изображений по порядку. CDN-адреса картинок в хэш не входят.
2. `ParsedRawRecord` получает необязательное поле `hashInput`; пайплайн считает `contentHash` от него, если оно передано, иначе — от `rawPayload`, как сейчас. Для family.by и ABWS поведение не меняется.
3. Скачиваются только изображения с новыми URL; для URL, уже известных по записи этого поста, берётся сохранённый `sha256`. Сменился только CDN-адрес — хэш поста тот же, модель не вызывается.
4. Модель вызывается только для новых записей и записей с изменённым `contentHash`. Каждый запуск пишет в `ImportRun` число вызовов модели, токены и модель; превышение бюджета источника на запуск откладывает оставшиеся посты до следующего запуска.

## Нормализация постов (LLM)

Новый нормализатор `normalizers/telegram-post.normalizer.ts` подключается в `import-normalization.service.ts` по `parserKey`, как сейчас `abws-event.normalizer.ts`. Модель вызывается только для новых и изменённых постов, через общий мультимодальный модуль.

**1. Предфильтр без модели — только бесспорные случаи.** Сразу `SKIPPED` получают опрос и пост без текста и без изображений. Отсутствие даты в тексте и короткий текст причиной отсева не являются, если у поста есть изображения: дата часто есть только на афише. Причина пишется в `qualityFlags.skipReason`.

**2. Один вызов модели** на пост через общий модуль: текст поста, ссылки и все фото альбома (до 10). Промпт отдельный от Capture — он про публичные мероприятия, а не про задачи семьи. Общие правила берутся из Capture: текст и картинки — данные, а не инструкции; ничего не выдумывать; у полей есть состояние `stated` / `inferred` / `missing`; год без указания — ближайшая будущая дата от даты поста; часовой пояс Europe/Minsk. Модель читает надписи на афишах; обычное фото используется только для понимания тематики, факты из него не выводятся. Результат Capture (`CaptureDraft`) в импорт не передаётся, у импорта своя схема.

```json
}
```

`from` — откуда взято значение: `TEXT`, `IMAGE:<index>` или `BOTH`. Если текст и афиша расходятся, в основное поле идёт значение из текста с `state = inferred`, а оба варианта — в `conflicts`. Запись с конфликтом в дате, времени или месте получает флаг `qualityFlags.conflicts` и повышенный приоритет в очереди; редактор видит оба значения рядом.

**3. Маппинг в `NormalizedEventImport`:** `occurrences[]` → сеансы (с `title` подсобытия для фестиваля), `ticketsUrl` → `performanceBuyUrl`, ссылка регистрации → `website`, фото поста → `mainImageUrl` + `imageUrls`, `confidence` и `audienceHint` → `qualityFlags`. Категория — существующим `detectEventCategory`.

**Правила по типам поста:**

| `postKind` | Что делаем |
| --- | --- |
| `EVENT` | Одна запись, обычный путь в матчер и очередь |
| `FESTIVAL` | Одна запись, подсобытия по дням — сеансы `ActivitySession` со своим `title` (пост Конкорса: 8 сеансов) |
| `DIGEST` | Дочерние записи `<канал>/<id>#1`, `#2`… в том же источнике и запуске, у каждой свой путь в матчер; родительская запись — `SKIPPED` с `skipReason = digest_split` |
| `NOT_EVENT` | `normalizeStatus = SKIPPED`, ревью-задача закрывается (`CANCELLED`) |

**Автоотсев после нормализации** (запись не попадает в очередь, задача закрывается, причина в `qualityFlags.skipReason`):

- все сеансы уже прошли — `past_event`;
- нет названия или ни одной даты — `incomplete`;
- город не в территории источника — `out_of_territory`.

**Возраст** заполняется, только если явно указан («6+», «для детей 3–7»). Иначе `ageText = null`, а `audienceHint` выводится в карточке ревью как подсказка.

**Изменённый пост** (новый `contentHash`) перенормализуется. Если запись уже опубликована, ревью-задача переоткрывается с флагом `sourceChanged`, и в карточке видно, какие поля изменились (дата, место, цена).

## Дедупликация

Существующий матчер (`event-match-scorer.ts` и соседи) дорабатывается, а не заменяется: так улучшение получают и family.by, и ABWS. Решение строится на четырёх признаках — место, дата, время, название.

**1. Поиск кандидатов** (`event-candidate-search.ts`), объединение по трём каналам:

- **по месту:** площадка сопоставляется через `venue-place-lookup.ts`; кандидаты — события этого `placeId`/площадки с сеансом `ActivitySession.startsAt` в день любого сеанса записи;
- **по дате:** события с сеансом в тот же день и похожестью названия ≥ 0.5 (текущий поиск по первому слову остаётся запасным);
- **среди ожидающих записей других источников:** `ImportedRecord` с `reviewStatus in (PENDING, IN_REVIEW)` и `normalizeStatus = SUCCESS` из других `ImportSource`, сеанс в тот же день. Это закрывает случай «пост и ABWS ждут ревью одновременно».

**2. Сравнение по сеансам**, а не по `nextOccurrenceAt`: для каждой пары берётся лучшая пара сеансов. Новый сигнал `startTimeDeltaMinutes`; совпадение времени — разница ≤ 30 минут. Если в посте нет времени, сигнал `null` и сильного совпадения быть не может.

**3. Нормализация.**

- `normalizeTitle` дополнительно убирает эмодзи, возрастные метки «(6+)», «0+» и служебные слова: спектакль, премьера, мастер-класс, МК, шоу, концерт, квиз.
- Исправить `normalizeAddress`: заменить `\b` на явные границы, рабочие для кириллицы (`(?<![а-яё])` / `(?![а-яё])`), и убрать этаж, «ТЦ», «ТРЦ» с названием. Покрыть тестами на «ул.», «пр-т», «пер.».

**4. Уровни решения** (поверх существующих `matchStatus` / `suggestedAction`):

| Уровень | Условие | `matchStatus` → `suggestedAction` |
| --- | --- | --- |
| 0. Тот же пост | Тот же `sourceId` + `externalId` | Обрабатывает пайплайн (хэш), без изменений |
| 1. Сильное | Место совпало + тот же день + время ±30 мин + название ≥ 0.8 | `MATCHED` → `UPDATE_EXISTING` |
| 2. Возможное | Место, день и время совпали, название < 0.8; или название ≥ 0.8 при другом месте/дне | `AMBIGUOUS` → `MERGE` (решает редактор) |
| 3. Нет | Ничего из выше | `NO_MATCH` → `CREATE_NEW` |

Уровни — это только рекомендация в карточке ревью: ни один уровень не сливает и не публикует запись автоматически, решение всегда за редактором. Совпадение только по месту и времени без названия не считается сильным: в одном ТЦ или театре в одно время идут разные события. Для фестиваля сравниваются и общее название, и названия подсобытий.

**5. Кандидат — ожидающая запись другого источника.** В карточке ревью она показывается рядом; действие «Это одно событие» связывает записи: обе получают одинаковый `publishedActivityId` после публикации любой из них, вторая закрывается как `APPROVED_MERGE`.

**6. Приоритет источников при слиянии — по полям, а не по источнику целиком** (`event-field-mapper.ts`, режим `UPDATE_EXISTING`):

| Поле | Приоритет | Почему |
| --- | --- | --- |
| Цена, сеансы, ссылка покупки (`performanceBuyUrl`, `buyUrl`) | ABWS > организатор > family.by > Telegram-агрегатор | Билетная система — источник истины по продаже |
| Описание, возраст, регистрация, контакты, соцсети | Организатор (его сайт или канал) > ABWS > family.by > Telegram-агрегатор | Первоисточник точнее агрегатора |
| Обложка | Фото организатора > ABWS > остальные | Права и качество |

- Источник с меньшим приоритетом только заполняет пустые поля; при расхождении непустых значений редактор видит оба и выбирает.
- Канал считается организатором по флагу источника `isOrganizerSource` (см. «Изменения схемы данных»).
- Поля под `ImportFieldOverride` не трогает никто — как сейчас.

**7. Учёт решений.** Сигналы матчера уже лежат в `matchCandidates`, решение — в `reviewDecision`. Отчёт (скрипт или страница в админке) раз в две недели: доля подтверждённых сильных совпадений по источникам. По нему настраиваем пороги; автоматического слияния нет и в этом релизе не планируется.

## Премодерация и расписание

Всё, что пришло из каналов, ждёт решения в существующей очереди `/admin/import/review`. Автопубликации нет; опубликованное событие создаётся со статусом `PENDING`, как сейчас.

**Плановые запуски:**

- Новая задача worker `imports.scheduled_runs` в `src/worker/index.ts` на существующем `Scheduler`, тик раз в 15 минут, своя `GlobalLock`-блокировка.
- Выбирает `ImportSource` с `isAutoUpdate = true`, `isActive = true`, `status = ACTIVE`, у которых `lastRunAt + runIntervalMinutes` уже наступил. Запускает их последовательно.
- `runImportForSource` принимает `triggerType` параметром и пишет `SCHEDULED` для плановых запусков (сейчас всегда `MANUAL`).
- Интервал по умолчанию для Telegram — 60 минут; для остальных типов `isAutoUpdate` остаётся выключенным, пока его не включат вручную.
- Запасной вариант без worker: cron-роут `/api/cron/import-scheduled` с `authorizeCronRequest`, та же функция внутри.

**Доработки очереди ревью:**

- Фильтр по типу источника и по конкретному каналу; бейдж Telegram и ссылка на исходный пост в карточке.
- В карточке: фото поста, сеансы списком, поля с низкой уверенностью помечены «проверить», у каждого значения — источник (текст или картинка №), противоречия текста и афиши показаны рядом, блок дублей с кандидатами из `Activity` и из ожидающих записей других источников.
- Пакетные действия по выделенным записям: «Опубликовать» (только `CREATE_NEW` с заполненными обязательными полями), «Отклонить». Сейчас пакетно есть только удаление.
- Счётчик автоотсева по причинам (`past_event`, `not_event`, `digest_split`) — чтобы видеть, что фильтр не режет лишнего.

**Сводка в Telegram** раз в день в 09:00 по Минску — в существующий админский канал уведомлений: «Каналы: 14 новых, 6 возможных дублей, 3 изменения в опубликованных; ждёт решения: 23» и ссылка на очередь.

## Контент и права

Из постов берём факты, а не тексты и не оформление: это контент чужих каналов.

- **Описание** всегда переписывается при публикации существующим AI-переписыванием в стиле редакции. Исходный текст остаётся только в `rawPayload`/`rawText`.
- **Обложка:** фото поста загружается существующим `optimizeImportedImage` как временная, с флагом `coverNeedsReplacement` в `qualityFlags`. Брендированные коллажи каналов-агрегаторов в публичную карточку не ставим; приоритет — фото организатора.
- **Ссылка на пост** видна только в админке. На сайте — ссылки организатора: регистрация, билеты, соцсети.
- **Хвост канала** (хэштеги районов, подпись канала, призывы подписаться) в данные не попадает; хэштеги районов можно передать подсказкой для города.

## Изменения схемы данных

Изменения аддитивные: два значения enum, три поля у источника, одно у записи, счётчики расхода модели у запуска. Новых таблиц и параллельных сущностей нет.

```prisma
enum ImportSourceType {
  // …существующие значения
  TELEGRAM_CHANNEL
}

enum ImportFetchStrategy {
  // …существующие значения
  TELEGRAM_WEB_PREVIEW
}

model ImportSource {
  // …
  /// Интервал плановых запусков при isAutoUpdate = true
  runIntervalMinutes Int     @default(60)
  /// Источник — сам организатор (приоритет по описанию, возрасту, регистрации)
  isOrganizerSource  Boolean @default(false)
  /// Бюджет вызовов модели на один запуск
  aiCallBudgetPerRun Int     @default(60)
}

model ImportedRecord {
  // …
  /// Родитель для записей, выделенных из поста-подборки (DIGEST)
  parentRecordId String?
  @@index([parentRecordId])
}

model ImportRun {
  // …
  aiCalls     Int @default(0)
  aiTokensIn  Int @default(0)
  aiTokensOut Int @default(0)
}
```

- `ParsedRawRecord.hashInput` — необязательное TypeScript-поле, без миграции: стабильное содержимое для `contentHash`.
- Изображения поста хранятся в `rawPayload.images[]` как `{ url, sha256, width, height }`; URL — для загрузки, `sha256` — для идентификации и хэша поста.
- `qualityFlags` (уже `Json?`) для Telegram заполняется всегда и со всеми ключами, как у ABWS: `skipReason`, `postKind`, `confidence`, `conflicts`, `audienceHint`, `sourceChanged`, `coverNeedsReplacement`.
- Источник каждого значения и противоречия хранятся в `normalizedData` вместе с нормализованным событием.
- `ActivitySession.source = "telegram"`, `externalId = <канал>/<id>#<n>` для сеансов из постов.
- Миграции — по принятой дисциплине: отдельный PR, проверка на `dev` до `prod`.
