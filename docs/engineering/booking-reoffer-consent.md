# Повторное предложение места: EVENT / зарегистрированный клиент

Scope PR #1327: только отклонённая STANDARD EVENT-заявка зарегистрированного клиента с датой/сеансом и проверяемым лимитом мест. Для гостей, OFFER/CLASS/CAMP/PLACE действие отсутствует. Feature flags занятий и праздников не меняются. Исходная REJECTED-заявка и её история сохраняются.

Один originalBookingId допускает одно предложение, включая завершённое/истёкшее. Уведомление отправляется через существующий registered-user канал после уникальной вставки. Повтор POST не создаёт второго предложения или уведомления. Создание предложения не резервирует место и не утверждает доставку внешним каналом.

Клиент принимает или отклоняет предложение самостоятельно. Согласие вызывает штатный createPublicBooking: Activity lock → BookingReoffer lock → свежая проверка собственности, статуса, даты, состава и вместимости → новая NEW-заявка и ACCEPTED в одной транзакции. Двойное согласие API возвращает один и тот же bookingId. Подтверждение бизнеса остаётся отдельным действием. Уменьшение вместимости, снятие лимита, смена режима на REQUEST_ONLY, закрытие/отзыв сеанса, архивирование события, отмена или истечение предложения запрещают новую запись. Guard режима и заданного лимита использует уже прочитанную под Activity lock конфигурацию, без дополнительного DB-запроса.

Предложение действует максимум 24 часа и не дольше начала сеанса (для записи на дату — конца дня по Минску). Истечение вычисляется при обращении без отдельного polling/cron. Бизнес определяется через активное OWNER/MANAGER-членство в бизнесе конкретной заявки, включая второй бизнес. Клиентский ответ проверяет customerUserId. Контакты не входят в reoffer DTO или уведомление; финальные SMS и contact projection #1325 сохранены.

Доступность читается только при открытии соответствующей карточки/предложения; нет запросов на каждую строку списка и общего приватного кеша. Клиентский GET дополнительно проверяет текущее событие и места. POST повторяет проверку в транзакции. SQL/p95 не измерены.

Проверки: API PostgreSQL включает отсутствие прав/отозванное членство, второй бизнес, cross-origin mutation, единственное уведомление при конкурентном создании, отсутствие приватных полей в DTO, два ACCEPT, DECLINE, EXPIRED, CANCELED, исчезновение события/сеанса, изменение лимита и гонку двух приглашений за последнее место. Внешние уведомления заменены mock. Реальные SMS не отправляются.

DEV UAT до merge: бизнес предлагает место → зарегистрированный клиент видит уведомление → выбирает ACCEPT/DECLINE → после ACCEPT появляется новая NEW-заявка → бизнес отдельно подтверждает. Сверить исходную REJECTED-историю, остальные поверхности #1325, контакты, мобильные размеры и feature flags. Изменение id/заявки во время ответа сервера не должно подменять состояние соседней карточки.
