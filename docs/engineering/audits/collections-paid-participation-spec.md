## 2. Принципы и инварианты

1. **Участие ≠ карточка.** Карточка — существующий Offer. Участие — долговечная запись об обязательстве (срок, оплата, hook, статус). Она переживает удаление Offer и связи.
2. **`ArticleLinkedItem` — только отображение.** Его удаление (в т. ч. каскадное) не стирает участие и не прекращает срок.
3. **Один источник сигналов персонализации** (раздел 4). Второй алгоритм не пишем.
4. **Профиль меняет только порядок.** Состав одинаков для всех. Платёж, Boost, пин не влияют на порядок.
5. **Ничего не продаётся из позиции.** Нет гарантии позиции или показов.
6. Не смешивать с `BillingAccount`, `BillingTransaction`, `Boost`, тарифом «Бизнес».

## 3. Модель данных (PR 1)

Изменения аддитивны. Миграции пишутся вручную в `prisma/migrations/…`, без `migrate dev`, без reset.

### 3.1 Article
- `collectionSlots Int?` — число мест. Только для `COLLECTION`. Задаёт редактор. CHECK: `NULL` или `>= 3`. Правило «опубликованных не больше slots» проверяется в сервисе.

### 3.2 `CollectionParticipation` (рабочее имя)
| Поле | Тип и правило |
|---|---|
| `id` | cuid |
| `articleId` | FK Article, **Restrict** (нельзя удалить подборку с активным участием; архивация через статус статьи) |
| `businessId` | FK Business, Restrict |
| `offerId` | FK Offer, **SetNull** + снимок `offerTitleSnapshot`. Участие переживает удаление Offer |
| `linkedItemId` | nullable, FK ArticleLinkedItem, **SetNull**. Связь отображения |
| `commercialStatus` | enum `INVITED / APPLIED / WAITLIST / PAID / EXPIRED` |
| `placementStatus` | enum `DRAFT / PENDING_MODERATION / PUBLISHED / HIDDEN` |
| `hook` | `VARCHAR(140)`, null допустим до подачи |
| `hookApprovedText`, `hookModeratedAt`, `hookModeratedById`, `hookModerationComment` | публикуется только утверждённый текст |
| `legacyPosition`, `legacyUntil` | nullable, парой (CHECK: оба null или оба заданы) |
| `priceAmount`, `currency` | снимок цены на момент счёта (по умолчанию 300 BYN) |
| `payerSnapshot` | JSON: УНП, название, банк, реквизиты (снимок на дату счёта) |
| `invoiceNumber`, `invoiceIssuedAt`, `paidAt`, `paymentConfirmedById` | оплата и подтверждение админом |
| `startsAt`, `endsAt` | срок 12 месяцев, считается от `paidAt` |
| `waitlistedAt`, `invitedAt`, `appliedAt` | метки |
| `replacedByParticipationId` | nullable, для замены предложения |
| `createdAt`, `updatedAt` | |

Ограничения:
- `UNIQUE(articleId, businessId, offerId)` где `offerId IS NOT NULL` (partial).
- Один живой (не `EXPIRED`) участник на пару `(articleId, offerId)`.
- `UNIQUE(articleId, legacyPosition)` где `legacyPosition IS NOT NULL`.
- CHECK: `PAID` ⇒ `paidAt, startsAt, endsAt, invoiceNumber` не null. `PUBLISHED` ⇒ `commercialStatus IN (PAID)` либо legacy.
- Отдельная таблица журнала `CollectionParticipationEvent` (аудит): смена статусов, кто, когда, причина. Без неё «история оплаты» не восстанавливается.

### 3.3 Расчёт квоты
- `editorialCount` = число `ArticleLinkedItem` без привязанного участия.
- `paidCapacity = slots − editorialCount − legacyOccupied` (legacy занимает slot).
- Публикация и перевод в `PAID`/`PUBLISHED` выполняются в транзакции с блокировкой строки `Article` (`SELECT … FOR UPDATE`), чтобы два параллельных подтверждения не превысили slots.
- Превышение ⇒ `WAITLIST` (автоматически при подаче заявки или подтверждении оплаты).

## 4. Единый источник персонализации (исследование переиспользования)

**Что нашёл (по коду на `0b22fc9e2`):**
- Общий ранкер: `planSuggestionScore` (`src/server/services/planSuggestions.service.ts:41`) = `engagementScore + interestBoost + experienceAffinityBoost`. Версия `engagement-profile-interest-experience-v3`. В `eventEngagementScores.ts` и `engagementWeights.ts` упоминаний boost/promo нет (проверено поиском). Для порядка этого достаточно: платёж и Boost в него не попадают.
- Возрастная логика: `confirmedAgeMatchAt`, `evaluateAge` (`familyPicks/select.ts`) — по подтверждённой дате рождения, консервативная (MONTH не равно точной дате).
- Слой выбора `selectPersonalFamilyPicks` делает **срез** (`resultCount`) и скрывает несовпадающих — для подборки это **нельзя** использовать как есть (профиль не должен ничего скрывать).
- `rankForFamily` — примитив сортировки, подходит.

**Расхождение, которое надо закрыть до PR 2:** `planSuggestionScore` и `familyPicks/load.ts` работают с **Activity (событиями)**: на входе `scheduleJson`, сеансы. Для **Offer** адаптера нет. Offer (занятия, лагеря, праздники) не имеет сеансов в том же виде.
Значит, нужен ограниченный шаг исследования в начале PR 2 (spike, 0,5 дня), результат которого записывается в этот документ:
1. Есть ли у Offer `interest`-сигналы, сопоставимые с `eventSystemInterestSlugs(scheduleJson)`; если нет — маппинг из `OfferCategory` и occasion/discovery signals.
2. Какой `engagementScore` у Offer (есть ли аналог `eventEngagementScores` для Offer).
3. Принимает ли `scoreCandidateExperienceAffinity` `categoryId`/`signalIds` Offer без изменений (по сигнатуре — да, `categoryId`, `discoverySignalIds`, `format`, `interestSlugs`).

**Решение по умолчанию:** новая тонкая функция `collectionOrderScore(item, familyContext)` строго составляет сигналы существующих функций (возраст из `confirmedAgeMatchAt`, интерес и опыт из `planSuggestionScore`-слоя `rankingSignals`) и не вводит новых весов. Если для Offer не хватает входных данных — Offer получает **нейтральное значение** (как «unknown»), порядок для него определяется редакционным score. Это согласуется с требованием «профиль меняет только порядок».

Запрещено в `collectionOrderScore`: читать `Boost`, `SearchDocument.boost`, `BoostSettings`, `BusinessPlacement`, оплату и `commercialStatus`. Контрактный тест (PR 2) проверяет это статически (список импортов) и поведенчески (одинаковый порядок при разных boost).

## 5. Порядок выдачи

**Редакционный порядок (гость, бот, SSR).** Детерминированный score: заполненность карточки, свежесть, возрастная универсальность. Рейтинг 5★ **обязателен** как компонент score (правило P0 от 2026-11-01); у объектов без оценок — нейтральное значение. Рейтинг участвует только в порядке и не скрывает размещение (В3). Источник — `FeedbackReputationAggregate.rankScore`; подключение к ранжированию подборки входит в PR 2. Тайбрейк: `position`, затем `id`.
**Персональный порядок (семья с профилем).** Тот же набор, порядок по `collectionOrderScore`.
**Legacy-позиции** фиксируются: `legacyPosition` N ставит элемент на место N в любой выдаче; остальные заполняют оставшиеся места по порядку.
**Ротация.** Только внутри близкого диапазона score (порог — параметр, например 5 % диапазона), seed = `articleId + дата (Europe/Minsk) + режим`. Для гостя и бота ротации нет (стабильный порядок).
**Кеш и приватность.** SSR остаётся с редакционным порядком (страница сейчас `force-dynamic`). Персональный порядок отдаёт только приватный endpoint с `Cache-Control: private, no-store`; ответ содержит только массив ID в порядке, без данных профиля. Семейные данные в публичный или CDN-кеш не попадают.

## 10. Решения владельца от 2026-11-05 (закрывают прежние открытые вопросы)

1. **Ранкер для Offer.** Старт с нейтрального значения и редакционного score; адаптер к общему ранкеру — исследование в начале PR 2. В редакционном score рейтинг 5★ обязателен, новые объекты без оценок получают нейтральное значение. Это порядок, а не скрытие (В3 не меняется).
2. **PR 7 не блокирует продажи.** Платное участие работает на PR 1–6 с редакционным порядком. PR 7 выпускается позже, когда будут данные по Offer.
3. **Счёт.** Одна сквозная серия номеров на все счета mamaGo (серия ИП). В назначении платежа указывается ID участия, чтобы оплату можно было сопоставить. Подтверждение поступления в первой версии остаётся ручным (В2); автосверка по выписке отложена. Обязательные реквизиты счёта сверяет бухгалтер.
   **Поправка по коду:** аудит не нашёл в коде существующего механизма генерации счетов (`/business/billing/documents` — только список; в `BusinessContract` счёт не формируется). Фраза «используем существующий механизм» верна только для номеров и реквизитов (`BillingPayerProfile`). Генерация счёта — новая работа PR 5; перед стартом PR 5 уточнить, в какой системе сейчас ведётся нумерация и откуда брать следующий номер.
4. **Порог ротации.** Оценки близки, если разница не больше 5 % нормализованного score. Порог в конфиге, калибруется по данным после запуска.
5. **Legacy-клиенты.** В базе списка, скорее всего, нет. Источник — акты, выписки, переписка. Шаблон CSV для `--dry-run` (разделитель запятая, UTF-8, первая строка — заголовок):
   `unp,business,article_url,position,paid_at,ends_at,amount`
   (по смыслу: УНП, бизнес, URL статьи, позиция, дата оплаты, дата окончания, сумма). Скрипт падает на неоднозначном бизнесе, статье или дубле позиции.
6. **Ранний переход.** Остаток старого срока сохраняется, к нему добавляется +3 месяца. Одна формула, без исключений: `endsAt = legacyUntil + 3 месяца`. Начало нового участия — дата оплаты; бонус в журнале пишется отдельной записью.
7. **Метка платности: НЕТ.** Публичной метки «Партнёр»/«Реклама» нет ни у платных участников подборок, ни у Boost-размещений. Платность видна только в кабинете бизнеса и админке. Внешний вид карточки платного и бесплатного участника идентичен. Следствия: в публичной разметке и JSON-LD нет признака платности; поле статуса участия не уходит в публичные ответы и в приватный API порядка (PR 7); тест на идентичность карточки добавляется в критерии PR 2. Редполитика: интро и вывод не обещают место и порядок.
   **Риск, зафиксированный без изменения решения:** ранее предполагалось, что распознаваемость платного размещения может требоваться законом о рекламе и вопросом доверия. Правовую оценку решения «без метки» дал или даст юрист; в репозитории такого заключения нет. Если заключение потребует маркировки, она добавляется отдельным PR и не ломает модель данных.
8. **PROD.** Выгрузка, а не доступ: владелец сам выполняет SQL из раздела 8 аудита и передаёт результат. До этого п. 9 этапа 0 остаётся открытым.
