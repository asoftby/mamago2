## 2. Принципы и инварианты

1. Продаём участие, а не позицию. Нет аукциона, гарантии позиции и доли показов.
2. **Участие ≠ карточка.** Карточка — существующий Offer. Участие — долговечная запись. `ArticleLinkedItem` отвечает только за отображение; его каскадное удаление не стирает участие.
3. Состав подборки одинаков для всех. Профиль меняет только порядок внутри slots, ничего не скрывает.
4. Boost, оплата, позиция и «Выбор редакции» не влияют на порядок и не продаются.
5. Платность видна только в кабинете бизнеса и админке. Публично признака нет ни в HTML, ни в API, ни в JSON-LD.
6. Не смешивать с `BillingAccount`, `BillingTransaction`, `Boost`, тарифом «Бизнес».
7. Редполитика: интро и вывод статьи не ссылаются на порядок и места.
8. Новые сущности запрещены, если можно расширить существующее (карточку «подборки» не создаём).

## 3. Модель данных (PR 1)

Миграции аддитивные, вручную в `prisma/migrations/…`; `migrate dev`, `db push` и reset не используются.

### 3.1 Article
`collectionSlots Int?` — только для `COLLECTION`, задаёт редактор. CHECK: `NULL` или `>= 3`.

### 3.2 `CollectionParticipation` (рабочее имя)
| Поле | Правило |
|---|---|
| `id` | cuid |
| `articleId` | FK Article, **Restrict** |
| `businessId` | FK Business, Restrict |
| `offerId` | FK Offer, **SetNull** |
| `offerTitleSnapshot` | название на момент последней публикации/подачи |
| `linkedItemId` | nullable FK ArticleLinkedItem, **SetNull** |
| `commercialStatus` | `INVITED / APPLIED / WAITLIST / PAID / EXPIRED` |
| `placementStatus` | `DRAFT / PENDING_MODERATION / PUBLISHED / HIDDEN` |
| `hookDraft`, `hookPublished` | оба `VARCHAR(140)`. Бизнес пишет `hookDraft`; публичным становится только `hookPublished`, который заполняется при одобрении модератором. До первого одобрения `hookPublished` пуст, и размещение не может стать `PUBLISHED` (hook обязателен для публикации). После выхода правка `hookDraft` не меняет публичный текст до одобрения. Также `hookModeratedAt/ById/Comment` |
| `priceAmount`, `currency` | снимок цены (по умолчанию 300 BYN) |
| `payerSnapshot` | JSON: реквизиты заказчика на дату счёта (из `BillingPayerProfile`) |
| `invoiceId` | FK на запись счёта (раздел 7) |
| `paidAt`, `paymentConfirmedById` | ручное подтверждение |
| `startsAt`, `endsAt` | `startsAt = publishedAt`, `endsAt = publishedAt + 12 мес.`; ставятся при переходе в `PUBLISHED`. Сроки до публикации пусты. `paidAt` на срок не влияет |
| `invitedAt`, `appliedAt`, `waitlistedAt` | метки |
| `replacesParticipationId` | nullable, замена предложения |

Ограничения:
- Одно живое (не `EXPIRED`) участие на `(articleId, offerId)` — partial unique.
- CHECK: `PAID` ⇒ `paidAt` не null; `PUBLISHED` ⇒ `startsAt`, `endsAt` не null.
- CHECK: `PUBLISHED` ⇒ `commercialStatus = PAID`.
- Статусы независимы: `HIDDEN` из-за выбывшего Offer не меняет `commercialStatus`.
- Журнал `CollectionParticipationEvent`: смена статусов, кто, когда, причина, предыдущее и новое значение. Без него история оплаты не восстанавливается.
- Реальные данные клиентов не попадают в миграции, тестовые фикстуры и репозиторий.

### 3.3 Квота и транзакция
- `editorialCount` = число `ArticleLinkedItem` без привязанного участия (редакционные события и предложения).
- `paidCapacity = collectionSlots − editorialCount`.
- Подтверждение оплаты и публикация выполняются в транзакции с блокировкой строки `Article` (`SELECT … FOR UPDATE`); если `paidCapacity` исчерпана, участие уходит в `WAITLIST`.
- Освобождение места (`EXPIRED`, снятие) **не продвигает** очередь автоматически: редакция выбирает следующего вручную.
- Уход в `WAITLIST` не создаёт счёта. Счёт выставляется только после решения редакции принять участие.

## 4. Единый источник персонализации

Факты (по `0b22fc9e2`, перепроверить на Этапе 0):
- Общий ранкер: `planSuggestionScore` (`src/server/services/planSuggestions.service.ts`) = вовлечённость + интересы + опыт; в файлах вовлечённости boost/promo не встречаются.
- Возраст: `confirmedAgeMatchAt` (`familyPicks/select.ts`).
- `selectPersonalFamilyPicks` обрезает список — **не используем**. `rankForFamily` — примитив сортировки, годится.
- Ранкер работает с Activity (события, `scheduleJson`). Для Offer адаптера нет. `FeedbackTargetType` содержит `OFFER`, так что агрегат репутации для Offer хранится.

Решение: PR 2 использует только редакционный score. PR 7 начинается с исследования адаптера Offer (интересы из категорий и сигналов Offer, `engagementScore` Offer, применимость `scoreCandidateExperienceAffinity`). Если данных не хватает, Offer получает нейтральное значение, порядок задаёт редакционный score. Новых весов и второго алгоритма не вводим. Запрещено читать в порядке: `Boost`, `SearchDocument.boost`, `BoostSettings`, оплату, `commercialStatus`, `placementStatus` (кроме фильтра «опубликовано»).

## 5. Порядок выдачи

**Редакционный (гость, бот, SSR).** Детерминированный score: рейтинг 5★ (обязателен; `FeedbackReputationAggregate.rankScore` объекта; нет оценок → нейтральное значение), заполненность карточки, свежесть. Тайбрейк: `position`, затем `id`. Рейтинг влияет только на порядок.
**Ротация.** Только если разница оценок ≤ 5 % нормализованного score (порог в конфиге), seed = `articleId` + дата (Europe/Minsk). Для гостя и бота страница стабильна в пределах суток.
**Персональный (PR 7).** Тот же набор, порядок по общему ранкеру в контексте подборки. Отдаётся приватным API `private, no-store` массивом ID; в ответе нет статуса оплаты и данных профиля.
**Кеш.** Гостевая версия — ISR с инвалидацией при любом изменении состава, hook, статусов и порядка. Сейчас страница статьи `force-dynamic`: переход на ISR — отдельная часть PR 2 с проверкой, что превью и предпросмотр не ломаются и старые URL открываются как раньше.
**JSON-LD.** Все карточки в SSR-HTML и `ItemList`; признака платности нет.

## 6. PR-план с критериями приёмки

Общее: отдельная ветка от свежего `origin/dev`; миграции проверяются на чистой БД и на копии prod; targeted тесты, ESLint, `tsc`; `--no-verify` и `migrate dev` запрещены.

### PR 1 — Данные
**Объём:** раздел 3, enum-ы, индексы, CHECK, журнал, чистая библиотека инвариантов (`computePaidCapacity`, `canConfirm`, переходы статусов).
**Приёмка:** удаление Offer не удаляет участие (`offerId = null`, снимок сохранён); удаление `ArticleLinkedItem` не удаляет участие; параллельные подтверждения при одном месте → один `PAID`, второй `WAITLIST`; нельзя опубликовать больше участников, чем `slots`; CHECK-и срабатывают; миграция проходит на чистой БД и копии prod.
**Тесты:** юнит на инварианты; PostgreSQL-интеграция (CHECK, partial unique, SetNull, конкуренция).
**Откат:** `DROP` новых таблиц и колонки (данных нет).

### PR 2 — Редакционный порядок и SSR
**Объём:** редакционный score с рейтингом 5★ и нейтральным значением, ротация ≤ 5 %, `ItemList`, гостевой ISR с инвалидацией, изоляция от Boost.
**Приёмка:** гость видит стабильный порядок, все карточки в HTML и `ItemList`; Boost и оплата не меняют порядок (параметризованный тест); **HTML карточки платного и бесплатного участника идентичен**; статус участия отсутствует в публичных ответах; состав не зависит от профиля; старые URL открываются как прежде.
**Замеры:** число SQL на страницу и время ответа до и после; кеш-попадания ISR. Если замер недоступен — явно указать.
**Откат:** флаг возврата на прежний порядок и режим `force-dynamic`.

### PR 3 — Кабинет бизнеса и бизнес-бот
**Объём:** раздел «Подборки»: приглашения, заявка, выбор своего опубликованного Offer, hook ≤ 140, статусы, блок «Подборки, куда вы подходите», замена выбывшего предложения через модерацию. Бизнес-бот: только текстовые уведомления с ссылкой на кабинет (действий в боте нет; доставка за `TELEGRAM_BUSINESS_DELIVERY_ENABLED`).
**Приёмка:** ACL по `businessId` и роли OWNER/MANAGER; чужое участие недоступно; повторная заявка идемпотентна; hook > 140 отклоняется на сервере; заявка сверх квоты → `WAITLIST`.

### PR 4 — Админка
**Объём:** `collectionSlots` и таблица участий в редакторе; подбор кандидатов расширением `EditorialRequest` (связь с подборкой) по категории, поводу, возрасту, территории; отметка и отправка приглашений; модерация hook и размещения; ручное управление листом ожидания; ручное подтверждение оплаты.
**Приёмка:** нельзя опубликовать больше участников, чем `slots`; платных не больше `slots − редакционные`; кандидаты — публичные Offer по существующим фильтрам; публикуется только `hookPublished`, заполняемый одобрением; отклонение hook оставляет `endsAt` пустым; публичный текст не меняется до одобрения правки; все изменения в журнале.
**Модерация hook:** `OfferRevision` не подходит (привязан к Offer), поэтому модерация идёт на самой записи участия (`PENDING_MODERATION`); подтвердить или пересмотреть на Этапе 0.

### PR 5 — Счёт, акт, срок
См. раздел 7.
**Конфиг и сроки:** `INVOICE_VALID_DAYS = 5` (календарных), `ACT_MODE = bilateral` по умолчанию; `unilateral` включается только после пункта в оферте. SLA модерации — 2 рабочих дня с момента оплаты; при отклонении hook срок не стартует (участие остаётся `PAID`, размещение не `PUBLISHED`, `endsAt` пуст). Нарушение SLA видно в админке и в журнале; возвратов нет.
**Приёмка:** уникальный номер `MG-ГГГГ-NNNN`, сброс по году, сумма прописью корректна, сохранённый PDF неизменен и не перегенерируется; без реквизитов плательщика счёт не создаётся; подтверждение оплаты идемпотентно; после истечения срока счёта участие не активируется; акт создаётся при переходе в `PUBLISHED`; `BillingTransaction`/`depositBalance`/`Boost` не затрагиваются (тест); выбывший Offer → `HIDDEN`, срок идёт, возврата нет.

### PR 6 — Уведомления и отчёты
**Объём:** новые значения `NotificationType` и сценарии в `notificationRegistry` (приглашение, заявка, лист ожидания, hook на правки/одобрен, счёт выставлен, оплата подтверждена, напоминания за 14 и 3 дня); cron по образцу `plan-event-reminders`; ежемесячный отчёт (показы, клики, заявки, распределение позиций); телеметрия `position`/`rankMode` в `article_performance_batch_v1`.
**Приёмка:** одно напоминание на порог без дублей; каналы по настройкам пользователя; цифры отчёта сверены на тестовом наборе событий; `CommercialNotification` не используется.

### PR 7 — Персональный порядок
**Объём:** исследование адаптера Offer (результат записывается в ТЗ), приватный API порядка, клиентская перестановка, фолбэк на редакционный порядок.
**Приёмка:** семья с профилем видит тот же состав в другом порядке; ничего не скрыто; ответ `private, no-store`; нет утечки статуса оплаты и данных профиля; измерены запросы к БД, размер и время ответа (или явно указано, что замера нет). PR 7 не блокирует продажи.

## 7. Счёт и акт (PR 5, пишется с нуля)

Существующее: `BillingPayerProfile` (реквизиты плательщика), список `/business/billing/documents`. Генерации нет.

- **Нумерация:** `MG-ГГГГ-NNNN`, последовательность PostgreSQL (отдельная на год либо сброс в транзакции), старт 1 в конфиге. Договоры не связываются.
- **Формат:** PDF из HTML-шаблона, сохраняется в хранилище при выставлении и не перегенерируется. Запись `Invoice` хранит номер, дату, срок действия, снимки, ссылку на файл, хэш PDF.
- **Реквизиты исполнителя — в конфиге:** ФИО ИП, юр. адрес, почтовый адрес, УНП, р/с, банк, БИК, номер и дата свидетельства, текст «Без НДС». Не хардкод.
- **Счёт-фактура:** номер, дата; «1-й экз. — заказчику / 2-й экз. — исполнителю»; основание: «к Публичной оферте mamaGo; оплата счёта является акцептом оферты»; исполнитель и заказчик (наименование, адрес, УНП, банк; заказчик из `BillingPayerProfile`); строка «Участие предложения «{offer}» в подборке «{article}» ({url})» | вид «Статья-подборка» | раздел «Журнал mamago.by» | 1 | начало и окончание размещения | сумма без НДС | «Без НДС» | 0 | итого; сумма прописью (BYN, рубли и копейки); срок действия счёта: дата + `INVOICE_VALID_DAYS` (5 календарных дней); назначение платежа: «Оплата по счёту MG-…, участие {participationId}».
- **Акт:** создаётся при переходе в `PUBLISHED`; номер = номер счёта, дата = начало размещения, те же строки. «В лице {signerName}, действующего на основании {signerBasis}» — необязательные поля `BillingPayerProfile` (в модели сейчас `signatoryName`, `signatoryBasis`; использовать их). Режим — флаг `ACT_MODE`: `bilateral` по умолчанию, `unilateral` после пункта в оферте.
- Подтверждение оплаты — вручную админом; автосверка по выписке не делается.
- Реальные данные клиентов в репозиторий и фикстуры не попадают.

## 12. Решения владельца от 2026-11-05 (закрывают вопросы v2)

1. Порога рейтинга для скрытия нет. `HIDDEN` — только снятие или недоступность предложения.
2. `endsAt = publishedAt + 12 мес.` SLA модерации — 2 рабочих дня с оплаты. При отклонении hook срок не стартует.
3. Модерация hook на записи участия: `hookDraft` / `hookPublished`; публичный текст меняется только после одобрения.
4. `INVOICE_VALID_DAYS = 5` (календарных). `ACT_MODE = bilateral` по умолчанию; `unilateral` — после пункта в оферте.

Открытым остаётся только порог ротации (значение конфига; по умолчанию 5 %).

### Следствия для реализации
- Участник платит до публикации, поэтому нужен видимый статус «оплачено, ждёт модерации» в кабинете и админке, а также метрика SLA (оплата → решение по hook).
- Если hook отклонён, бизнес правит `hookDraft` и подаёт снова; платёж не возвращается, срок стартует с публикации.
- Если размещение не выходит из-за отклонений дольше разумного срока, это решает редакция вручную; автоматического возврата и автоматического истечения оплаты нет (при необходимости — отдельное решение владельца).
