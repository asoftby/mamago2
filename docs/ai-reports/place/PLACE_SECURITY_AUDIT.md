# Place Security Audit - Результаты

## Дата аудита
7 марта 2026

## Проблема
Пользователь сообщил, что во вкладке "Архив" отображается место, которое он не добавлял.

## Проведенный аудит

### 1. Проверка схемы данных
✅ Place модель использует `ownerUserId` (связь с User)
✅ `ownerUserId` - обязательное поле (NOT NULL)
✅ Архивация через поля `archivedAt` и `archivedByUserId`

### 2. Проверка данных в БД
Найдено:
- **User 1** (`asoftby@gmail.com`): 2 места (1 активное, 1 архивное)
  - Активное: "Корректное название"
  - Архивное: "E2E Test Cafe"
- **User 2** (`test-business@example.com`): 6 мест (все активные)

**Вывод**: Архивное место "E2E Test Cafe" принадлежит User 1 и правильно отображается только у него.

### 3. Проверка кода фильтрации
**ДО исправлений**:
- ✅ Страница фильтровала по `ownerUserId: user.id` - правильно
- ⚠️  Логика фильтрации дублировалась в разных местах
- ⚠️  Не было проверки наличия Business entity
- ⚠️  Archive service дублировал логику проверки владельца

### 4. Тесты безопасности
Все тесты прошли успешно:
- ✅ Пользователи изолированы друг от друга
- ✅ Невозможно архивировать чужое место
- ✅ Фильтрация архива работает корректно
- ✅ Все архивные места принадлежат правильным владельцам

## Реальная причина "бага"

**Бага НЕ было**. Пользователь видел свое собственное тестовое место "E2E Test Cafe", которое он создал для тестирования и заархивировал.

Однако были найдены **архитектурные проблемы**:

1. **Дублирование логики** - фильтрация мест повторялась в разных местах
2. **Отсутствие централизованного сервиса** - нет единой точки для работы с местами
3. **Слабая проверка Business** - не проверялось наличие Business entity
4. **Отсутствие логирования** - сложно отследить операции архивации

## Внесенные улучшения

### 1. Создан централизованный Place Service
**Файл**: `src/server/services/place.service.ts`

Функции:
- `getBusinessPlaces()` - получение мест с фильтрацией
- `userOwnsPlace()` - проверка владения
- `getPlaceForOwner()` - получение места с проверкой владельца

**Преимущества**:
- Единая точка фильтрации
- Гарантированная безопасность
- Переиспользуемый код
- Легко тестировать

### 2. Улучшен Archive Service
**Файл**: `src/server/services/placeArchive.service.ts`

Изменения:
- Использует `getPlaceForOwner()` для проверки владельца
- Добавлено логирование операций
- Упрощена логика (меньше дублирования)
- Более понятные сообщения об ошибках

### 3. Улучшена страница "Мои места"
**Файл**: `src/app/business/(protected)/places/page.tsx`

Изменения:
- Добавлена проверка наличия Business entity
- Использует централизованный `getBusinessPlaces()`
- Редирект на onboarding если нет Business
- Логирование предупреждений

### 4. Создан тест безопасности
**Файл**: `scripts/test-place-security.ts`

Проверяет:
- Изоляцию пользователей
- Защиту от кросс-юзер операций
- Корректность фильтрации архива
- Владение архивными местами

## Архитектурные рекомендации

### Текущая архитектура
```
User (BUSINESS_OWNER) → Place
         ↓
      Business
```

Place связан с User, а не с Business.

### Проблемы текущей архитектуры
1. Если в будущем у User будет несколько Business - будет проблема
2. Нет явной связи Place → Business
3. Сложно делать бизнес-аналитику по Business

### Рекомендация для будущего
Рассмотреть миграцию на:
```
Business → Place
    ↓
  User (owner)
```

Но это требует:
- Миграцию данных
- Обновление всех запросов
- Изменение API
- Тестирование

**Для MVP текущая архитектура приемлема**, так как:
- One business per owner (ограничение MVP)
- Все работает корректно
- Безопасность обеспечена
