# UI Component Rules

Дата фиксации: 2026-05-15

## Главный принцип

`ActivityCard` является единым UI-шаблоном для публичных карточек активностей: `events` + `offers`.

## Что запрещено

1. Нельзя создавать новые отдельные публичные карточки:
- `EventCard`
- `OfferCard`
- `PlanEventCard`
- `PlanOfferCard`

2. Нельзя зашивать конкретные действия внутрь shell карточки:
- `Добавить в план`
- `Убрать`
- `Купить билет`
- `В идеи`

3. Нельзя использовать `ui-lab` как место хранения production-компонентов.

## Что разрешено

1. Различия по контексту решаются через props:
- `variant`
- `density`
- `actions`

2. Различия по данным решаются через нормализованную UI-модель:
- `ActivityCardItem`

3. Различия по сценарию решаются отдельными action-компонентами:
- `ActivityActionsFeed`
- `ActivityActionsPlan`

## Правила для ActivityCard

1. `ActivityCard` должен быть независим от Prisma `Event` / `Offer`.

2. `ActivityCard` должен принимать только нормализованный item:
- `item: ActivityCardItem`

3. `ActivityCard` должен быть presentation-first компонентом.

4. Бизнес-логика даты, цены, статуса, сохранения и планирования должна жить:
- в мапперах;
- в feature-level actions;
- в контейнерах страниц;
а не внутри самой карточки.

## Правила для event / offer унификации

1. `events` и `offers` используют один и тот же UI shell.

2. Различия между `event` и `offer` должны отражаться через:
- данные `ActivityCardItem`
- `badgeLabel`
- `dateLabel`
- `priceLabel`
- `statusLabel`
- выбранный `actions` slot

3. Если нужен новый визуальный сценарий, сначала надо проверить, покрывается ли он:
- существующим `variant`
- существующим `density`
- новым action slot

Только если это невозможно, обсуждается расширение базового `ActivityCard`.

## Правила для “Моего плана”

1. Для “Моего плана” используется тот же `ActivityCard`, а не отдельная карточка.

2. Контекст плана задаётся через:
- `variant="plan"`
- `actions={<ActivityActionsPlan ... />}`

3. Плановые действия не должны форкать shell карточки.

## Правила для повторяемых publication blocks

1. `LocationBlock` и другие повторяемые блоки должны быть общими компонентами.

2. Повторяемые блоки страниц событий / предложений / мест нельзя бесконечно реализовывать inline в page-view компонентах.

3. Для следующих типов блоков нужно идти к общим компонентам:
- `LocationBlock`
- `ScheduleBlock`
- `PriceBlock`
- `GalleryBlock`
- `ReviewsBlock`

4. Если блок отличается только текстом, данными или CTA, это не повод создавать новый shell.

## Правила для состояний

1. `EmptyState`, `LoadingState`, `ErrorState` должны постепенно унифицироваться как переиспользуемые UI-patterns.

2. Нельзя создавать новые одноразовые empty/loading/error реализации без причины.

3. Если временно нужен inline-state, он должен быть помечен как кандидат на будущую унификацию.

## Правила для ui-lab

1. `ui-lab` является витриной компонентов, а не местом хранения компонентов.

2. В `ui-lab` допустимы:
- mocks
- showcases
- comparison states
- migration previews

3. В `ui-lab` недопустимо переносить production-компоненты “для порядка”.

4. Любая правка в `ui-lab` должна помогать проверять source-компонент, а не дублировать его реализацию.

## Правило миграции

1. Старые компоненты не удаляются до полной миграции.

2. Переход выполняется точечно, по use-case:
- сначала новый foundation;
- потом ограниченный перенос конкретной страницы;
- потом удаление legacy после проверки usages.

3. Любая новая публичная карточка активности должна сначала рассматриваться как конфигурация общего `ActivityCard`.
