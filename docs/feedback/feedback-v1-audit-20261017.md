# mamaGo Feedback 1.0 — аудит и корректировки (17.10.2026)

Основа: пользовательская PDF-спецификация (10 страниц). Это не подтверждение юридической трактовки.

## P0: проверено в dev

- `src/app/api/plan/experiences/[id]/feedback/route.ts`: телефон обязателен даже если `comment=null`. Должна быть частная реакция без телефона, публичный текст — только после SMS и модерации.
- `PlaceReview` смешивает `MAMAGO`/`GOOGLE`, а карточка места объединяет их при расчёте звёзд. Расчёты следует разделить до публичного запуска Feedback.
- `ArticleRating`, `RouteRating` используют `identifier`, включая гостей (иногда IP). Новый актор не может иметь общее значение anonymous, перенос сырых IP запрещён.
- `PlaceReview` не хранит userId, исторический автор только `authorName`; обратная привязка по совпадающему имени недопустима.
- Пользовательские PK в проекте — cuid string, не UUID. Prisma/PostgreSQL `NULL` в составном UNIQUE не предотвращает дубли.

## Скорректированное проектное решение

1. Базовая модель: `FeedbackReaction`, `FeedbackReview`, `FeedbackTag`, `FeedbackReputationAggregate`. Одна реакция на actorKey / target / occurrenceKey. occurrenceKey — обязательный текст, пустая строка только для контента без сеанса. Непосредственная привязка к сеансу должна проходить серверную валидацию.
2. `value=-1/0/+1`; содержание статей и breaking news остаётся в сущности Article до появления отдельной модели новостей. Для исторических маршрутов — `ROUTE`.
3. `actorKey`: user:<cuid> или guest:<opaque ID>; не сохранять IP в открытом виде, анонимные миграционные идентификаторы хешировать ключом миграции; сохранённый source ID — технический идемпотентный ключ.
4. `isPublicEligible=false` по умолчанию. Для реакций/тегов без идентификации использовать только частную аналитику до юридического заключения. Публикация публичной реакции — отдельное контролируемое решение, не автоматическое следствие нажатия.
5. Текст — одна запись на реакцию; SMS + модерация до публикации. При повторной правке текст возвращается в PENDING, опубликованную версию при необходимости сохранять до повторного решения.
6. Scope program / venue / organizer применяется только при наличии реальной связи и в контексте фактического посещения; реакция на спектакль не означает оценку здания. Двойной подсчёт исключить на уровне проекции. Никаких персональных заметок в репутации.
7. Показ: 0 — «Оцените первым»; 1–4 — число без процента; от 5 — доля положительных; индекс ранжирования отдельно с априорным весом 10 и повышением за подтверждённый визит. Проверять воздействие малого n.
8. При выборе эмодзи личная реакция сохраняется сразу; теги до 3 на компактной форме; сохранение с debounce или последовательными ревизиями, без гонок ответов. Изменение старого текста — новая модерация.
9. Родительский возраст не выводить из конкретной семьи наружу. Срезы — только агрегированные возрастные группы при достаточном размере выборки; обязательно учитывать состав посещения, не все дети автоматически присутствовали.
10. Google Places: не копить копии текстов/авторов бессрочно; хранение только разрешённого metadata (в частности Place ID), запрашивать актуальный контент и соблюдать атрибуцию. Текущие копии не удалять без отдельного безопасного плана.
11. Никаких запусков push до общего rate limit для семьи, проверки напоминаний и настроек согласия/уведомлений. Время окончания должно определяться по реальному сеансу, а не по дате начала.
12. Без перезаписи старых таблиц на первом этапе. Shadow-read, сверка количества, идентичности и происхождения, аудит прав на private/FAMILY, backfill идемпотентный и возобновляемый.

## План безопасной реализации

**A (текущий PR):** добавить типизированные таблицы и индексы, чистые функции подсчёта/дедупликации/eligibility с тестами. Старые чтения и запись не меняются; миграция только добавляющая.

**B:** серверные endpoints + интеграция Experience (частная реакция без номера, публичный текст с SMS), dual-write/теневая сверка. Отдельно миграции ArticleRating и RouteRating, включая hashed guest legacy ID.

**C:** единый компонент на карточках события/места/предложения/статьи, справочник чипов в admin, аналитика и модерация.

**D:** отделение Google, публичные агрегаты и linked reputation после юридической проверки; B2B аналитика и push после нагрузочных испытаний.

## Важно для деплоя

Не применять Prisma migration до проверки на копии DEV, `prisma validate`, `migrate status`, `check:push`, CI, аудит количества записей и плана отката. Отдельное разрешение на перенос DEV/PROD.
