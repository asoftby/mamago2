# Feedback 1.0 — Репутация места из нескольких источников (решение 17.10.2026)

## Продуктовое решение

Площадка должна показывать **всю доступную картину**: Google Maps, прямые реакции на место, реакции на проходившие здесь события и отзывы об услугах, реально оказанных на этой площадке.

Это расширяет покрытие впечатлений, но **количество оценок не является единым качественным баллом**.

### Главное различие

- **Объём свидетельств** (`totalSignals`) = Google `userRatingCount` + опубликованные прямые оценки mamaGo места + связанные оценки посещённых здесь событий + оценки услуг, оказанных на этой площадке.
- `totalSignals` — число оценок из разных источников, **не число отзывов с текстом и не число уникальных посетителей**. Один человек может оценить место и событие; Google-автора невозможно надёжно сопоставить с пользователем mamaGo. В местах, где нельзя соблюсти правила Google Maps по атрибуции и совместному отображению, НЕ публиковать суммарное число с Google; показывать суммы раздельно.
- **Качество площадки**: прямые оценки самой площадки + только venue-специфичные сигналы из событий/предложений. Общая оценка спектакля или услуги НЕ переносится в качество здания/персонала автоматически.
- **Качество впечатлений на этой площадке**: публичные реакции о прошедших здесь событиях и оказанных здесь услугах, в собственном, подписанном распределении. Этот показатель показывает, что здесь интересного, а не только свойства локации.
- **Google**: звёзды (например `★4,6`) и `userRatingCount` — отдельное представление с названием «Google Maps». До пяти returned text reviews ≠ userRatingCount. Не преобразовывать Google 1–5 звёзд в mamaGo −1/0/+1 и не выдавать объединённый процент как «рейтинг Google» или «рейтинг mamaGo». Проверить terms/cache/attribution перед выпуском.

## UX карточки места (прототип)

**Отзывы и впечатления**

- `Google Maps · ★ 4,6 · 320 оценок` (официальный источник/атрибуция)
- `mamaGo · 75 оценок` — переключатель «О месте — 15», «На событиях — 40», «Об услугах — 20»
- Основные venue-теги: «Удобно с коляской», «Чисто», «Тесно» — всегда с указанием `из X оценок`.
- Если юридическое и платформенное согласование разрешит, можно выводить `395 оценок из разных источников`, но рядом раскрыть слагаемые и понятное предупреждение об уникальности. Без разрешения выводить две группы отдельно.
- Отдельный блок «Как здесь проходят события/услуги» со своей оценочной метрикой и количеством мнений.
- Источник каждого текстового отзыва виден; для Google показывать ссылки автора и конкретного отзыва, если доступны API.

## Правила выборки и дедупликации

1. Связать `FeedbackReaction.EVENT` с Place только по неизменяемому `FeedbackReaction.venuePlaceIdAtVisit`, записанному сервером в момент подтверждённого визита. Ни текущий Place события, ни изменяемый `PlanItem.venuePlaceId` не считаются достаточным доказательством.
2. `FeedbackReaction.OFFER` относится к Place только если его `venuePlaceIdAtVisit` совпадает с местом подтверждённого оказания услуги; HOME/OUTDOOR/выездная услуга без подтверждённого venue не включаются.
3. Один `reactionId` может входить в несколько аналитических проекций, но в `totalSignals` места его можно считать только раз. Дубли `Experience`/`BookingFeedback` с одинаковым фактическим взаимодействием при миграции разрешаются через origin idempotency mapping, а не по имени.
4. Публичные показатели берут только `isPublicEligible=true`, ответы `PUBLISHED`, соответствующие правилам доступа и юридической политике. Данные из Family PRIVATE и заметки никогда не переносятся в публичную репутацию.
5. Прямые реакции / связанные с событиями / предложения / Google — разные источники, не смешивать ни метрики качества, ни подписи к ним.
6. Не выводить проценты при выборке <5. Для связанных тегов использовать отдельный порог и минимальное число независимо подтвердивших пользователей.
7. `Google.userRatingCount` может включать оценки без текста; выводить «оценок», никогда автоматически не писать «отзывов».

## Схема и этапность

Таблица `FeedbackReaction` уже содержит `targetType`, `targetId`, `occurrenceKey`; `FeedbackReputationAggregate` содержит отдельные поля `linkedTags`. Не менять foundation migration на основании предлагаемого индекса, пока не выполнено исследование фактических связей event/session/offer/place.

Следующий отдельный PR: read-only `PlaceReputationOverview` (Google metadata + прямые Reaction + linked EVENT/OFFER + venue-теги), тесты на несколько событий в одном месте, смену площадки, выездные услуги, двойной подсчёт и анонимные/частные реакции. Затем подключить UI с breakdown. **Не включать новый публичный составной рейтинг до юридического и платформенного согласования.**
