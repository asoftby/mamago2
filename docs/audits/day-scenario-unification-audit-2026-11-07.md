## 5. Решения владельца (по итогам PR 0)

1. UI — по макету «просто»; движок проектируем под полное ТЗ (диапазон,
   `pinned`, режимы передвижения заложены в модель, в UI скрыты).
2. Task 7 не оставляем параллельно и не переименовываем — новый сценарий
   строится на нём: `DayScenario` (unique `userId+date` остаётся) — сохранённый
   сценарий; `/api/plan/scenario` (idempotency, fingerprint) расширяем;
   `scenarioTravel.ts` расширяем режимами и кэшем `TravelEstimate`;
   `detectScenarioConflicts` переиспользуем; `ScenarioDraftEditor` эволюционирует
   в редактор черновика внутри виджета. Страницу
   `/[city]/my-plan/[date]/scenario` и `DayScenarioBlock` удаляем в PR 4;
   кнопку «Собрать сценарий дня» заменяем точками входа из макета.
3. «Выходные» = два дня, табы Сб/Вс (гостевой генератор уже умеет 2 дня).
   Произвольный диапазон до 3 дней — не в MVP, но модель его поддерживает.
4. Квота гостя списывается только первой сборкой на новую дату. «Другой вариант»
   и «Заменить» квоту не тратят; ограничение — rate limit 30/мин
   (`rateLimit.ts`). Регистрация — на «Сохранить».
5. PR 1a (без изменения поведения): вынести `KickerLine`, `ConfirmBar`,
   `DateSlider` и токены `C` из `SaveToPlanModal` в общий модуль на базе
   `myPlanV3Tokens`; `SaveToPlanModal` переходит на них. UI сценария собирается
   из них + `SaveFlowContainer`, `PlanScreenHeader`, `planChipStyles`.
6. Передвижение: в UI «на машине», но при пешем < 15 мин показываем «пешком».
   Режим хранится в модели.
7. Удаляем целиком в PR 4: `weekend/page`, `WeekendPlanner`, `weekendRules`,
   `/api/admin/weekend`, `weekendPlanner.service`, ссылку в `CityShell`. Ранкер
   и его потребители (Telegram, familyPicks) не трогаем.
8. Учёт записей плана: исключать и подстраиваться под все записи на дату —
   активности, места и заметки со временем.
9. Перед PR 1 — baseline (раздел 6).
10. Отчёт оформлен этим документом.
11. Порядок: сначала закрыть блокер RC1 #1103 → PR 1a → PR 1 → PR 2–4.

## 6. Baseline горячего пути (до PR 1)

Метод: throwaway-скрипт вызывает те же функции, что маршруты
(`rankPlanSuggestionsForCity`, `confirmedGuestPlanOccurrences`,
`quickGuestQuotaGate`, `recordGuestSuccessfulGeneration`,
`recordRecommendationRun`, `planItem.findMany`), считая события Prisma `query`
(`NODE_ENV=test PRISMA_QUERY_EVENTS=1`); 30 запусков после прогрева, локальный
Postgres (docker), дата 2026-11-07.

| Эндпоинт | БД-запросов за вызов | p50 | p95 |
|---|---|---|---|
| `POST /api/plan/generate` (гость, 1 день, без фильтра возраста) | **22** (включая записи: квота, trace-run, exposures) | 11.7 мс | 14.6 мс |
| `GET /api/plan/suggestions` (залогиненный, без персон) | **15** (включая запись trace-run) | 7.7 мс | 9.5 мс |

**Ограничения (не выдавать за прод-метрики):**
- В локальной БД 21 опубликованное событие, 2 места, не более 1 события на
  дату: число запросов отражает структуру кода, а не объём; **p50/p95 не
  репрезентативны** (нет сетевой задержки, нет реальных объёмов).
- Измерены не HTTP-маршруты, а их БД-часть; Next.js-рендер, аутентификация и
  cookie-слой не включены. Для `suggestions` не измерены ветки с персонами
  (`buildSelectedProfileContext`, `resolveSelectedExperienceAffinity`).
- Репрезентативный p95 требует DEV с реалистичным каталогом: HTTP-замер на DEV
  (с персонами и без) — **обязательное условие перед PR 1**, не опция.
- Критерий для PR 1: «Другой вариант» и «Заменить» в пределах TTL кэша пула — 0
  запросов к БД для чтения пула (проверка по логам); число запросов на
  первую сборку не должно расти относительно baseline без обоснования.
