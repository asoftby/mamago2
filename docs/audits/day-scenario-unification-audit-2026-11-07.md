## 8. Кластеризация и режимы передвижения (решения владельца от 2026-11-07)

Дополнение к ТЗ движка. Реализация — в составе PR 1, порядок прежний: после
закрытия RC1 #1103 и baseline на DEV.

**Предварительные факты** (по `schema.prisma` на `e6a9fcd90`, проверяются
аудитом п. 0):

- `Place.lat/lng` (`Float?`) и `Place.territoryId` есть; у `Activity` своих
  координат нет — только `placeId` (`Activity.placeId`), `territoryId` и
  `metroStationId` (у `MetroStation` есть `lat/lng`).
- `Territory` — иерархия **COUNTRY → REGION → CITY**; уровня «район» в ней нет.
  Административный район живёт в отдельной модели `District`, ссылки на которую
  у `Place`/`Activity` нет.
- Единственная реализация расстояний — `src/lib/geo/haversineMeters.ts`
  (+ `scenarioTravel.ts`, `listNearbyCities.ts`, `place-match-scorer.ts`);
  geohash и гео-индексов нет.

**Решение по «району» (закрыт открытый вопрос, 2026-11-07).** Административные
районы **не используем**: в Минске это радиальные клинья, они плохо отражают
близость. Кластеры — **только на geohash**, без новых сущностей и без связи
`Place` → `District`:

- `geoCell6` (geohash-6, ≈ 1,2 × 0,6 км) + соседние ячейки — уровень «рядом»,
  основной для режима «Пешком»;
- `geoCell5` (geohash-5, ≈ 5 км) — крупный кластер вместо «района» для режима
  «Машина»: предпочтение той же/соседней ячейки-5, максимум один переход между
  ячейками-5 за день считается «дальним переездом»;
- оба значения хранятся у `Place`; `Activity` получает их через `placeId`
  (собственные координаты `Activity` не добавляем, колонок `geoCell*` у
  `Activity` нет);
- `Activity` без `placeId`: в пешем режиме **исключается**; в режиме «Машина»
  допускается с координатами станции метро как приближением (`metroStationId`)
  и пометкой «примерное место» в UI;
- подписи вида «во Фрунзенском» и работа с `District` — **не в MVP**
  (BACKLOG-232).

**Решения:**

0. **Аудит перед реализацией.** Какие гео-поля уже есть у `Place`/`Activity`
   (координаты, адрес, привязка к `Territory`), как `Activity` связано с местом
   проведения (в т.ч. онлайн / без места / несколько мест), есть ли
   geohash/гео-индексы и расчёты расстояний кроме `scenarioTravel.ts`.
   Переиспользуем и расширяем, не дублируем. **Короткий отчёт — в начале PR 1.**
   Вопрос «чем считать район» закрыт решением выше.
1. **Кластеры считаются при записи, не при сборке.**
   - `geoCell6` и `geoCell5` у `Place` (две nullable-колонки + индексы под
     запросы пула; `Place.territoryId` остаётся грубым фильтром города/области);
   - проставлять при создании / обновлении координат / импорте; одноразовый
     бэкфилл существующих `Place`; аддитивная миграция — вручную (правила
     миграций репозитория: без `migrate dev`, без `db push`);
   - `Place` без координат — `geoCell*` = `NULL`, вне пешего режима.
2. **Пул кандидатов в кэше** индексируется по `geoCell6` и `geoCell5`; соседние
   ячейки находятся вычислением (таблица соседей geohash), без запросов в БД.
   Пересборка в пределах TTL остаётся без обращений к БД.
3. **Сборка:** якорь (точное время или лучший скоринг) → кандидаты со штрафом
   за удалённость от якоря и от предыдущей точки; сила штрафа зависит от
   режима.
4. **Режим «Пешком»** (жёсткие ограничения):
   - только та же и соседние `geoCell6`; переход ≤ 15 мин (~1,2 км), иначе
     точку не ставим;
   - сумма за день ≤ 3 км (с ребёнком 0–3 — ≤ 2 км); цепочка без возвратов
     (отдельного «района» нет — «рядом» задаётся ячейками-6);
   - `Activity` без `placeId` и `Place` без координат исключаются;
   - если кандидатов не хватает — состояние «Рядом мало вариантов —
     переключиться на машину?».
5. **Режим «Машина»** (гибкие ограничения):
   - весь город, предпочтение той же/соседней `geoCell5`; переход
     предпочтительно ≤ 25 мин, > 40 мин — предупреждение «Далеко — заменить?»;
   - максимум один переход между ячейками-5 за день («дальний переезд»); штраф
     растёт с суммарным временем в пути; порядок точек — без петель;
   - `Activity` без `placeId` допускается с приближением по станции метро и
     пометкой «примерное место».
6. **Режим «Транспорт»** — промежуточные коэффициенты, в UI пока скрыт.
7. **Выбор «Пешком / Машина» возвращается в UI**: переключатель в черновике,
   значение сохраняется в профиле семьи; дефолт — машина. Это осознанное
   отклонение от макета «просто» (правило подписи из раздела 5 — «на машине»,
   «пешком» при переходе до 15 мин — остаётся: подпись показывает фактический
   режим перехода).
8. **Время в пути** — по-прежнему haversine-оценка + кэш `TravelEstimate`,
   без внешних API.

**Следствия для PR 1 / рисков:**

- Колонки `geoCell6`/`geoCell5` у `Place` нужны вместе с бэкфиллом; при каждой
  записи координат `Place` (создание, правка, импорт,
  `resolvePendingLocationOnPublish`) значения должны пересчитываться — иначе
  кластеры разъедутся. Покрыть тестом на каждый путь записи, найденный аудитом
  п. 0. Единая функция «координаты → geoCell6/geoCell5» живёт в одном месте
  (рядом с `src/lib/geo/`).
- Если у `Place` меняются координаты, кэш пула инвалидируется по обычному TTL;
  принудительная инвалидация — только при подтверждённой необходимости.
- Профиль семьи получает поле режима передвижения (аддитивная миграция,
  nullable, дефолт «машина» на чтении).
- Пеший режим — единственный режим с жёсткими «нет точки»: нужен явный
  результат движка «мало вариантов» (а не пустой сценарий), чтобы UI показал
  переключение на машину без повторной сборки вслепую. Метка «примерное место»
  — признак в результате движка, а не в данных `Activity`.
- Модель `TravelEstimate` (раздел 7) хранит режим в ключе
  `(fromPlaceId, toPlaceId, mode)`; для 0–3 лет лимит 2 км применяется на
  уровне сборки, а не в кэше расстояний.
