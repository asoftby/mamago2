## 2. Разбивка PR 3

Один PR на весь объём не проверяем: миграция + транзакционная запись + четыре UI-поверхности + публичная страница + гость.
Предлагаем три PR, все за тем же флагом, каждый с отдельным откатом:

- **3a (этот PR):** миграция (`PlanItem.scenarioId/timeType/pinned`, `DayScenario.groupId/source/legsJson`), сервис и маршрут
  `POST /api/plan/day-scenario/save` (один день и «выходные» в одной транзакции, идемпотентность), кнопка «Сохранить в план» /
  «Сохранить выходные» в черновике с состоянием успеха. Существующие записи плана не меняются.
- **3b:** плашка «День от mamaGo · N мест» с меню ⋯ (Изменить, Удалить этот день, Удалить выходные), ✦ в ленте дат, ссылка на парный
  день, «Изменить день» (черновик с текущими точками), режим передвижения в профиле семьи.
- **3c:** «Поделиться» (read-only страница дня/выходных), гость: черновик переживает вход/регистрацию и применяется
  автоматически, квота гостя — только первая сборка даты.

## 3. Решения 3a

1. **Модель.** `PlanItem.scenarioId` (nullable FK на `DayScenario`, `ON DELETE SET NULL`), `timeType` (`CONFIRMED|SUGGESTED`, nullable),
   `pinned` (bool, default false). `DayScenario.groupId` (nullable, общий для Сб/Вс), `source` (`'ENGINE'` для дней, собранных движком;
   null для дней редактора Task 7), `legsJson` (время в пути между точками: `[{ planItemId, mode, minutes, distanceM }]`).
   Все изменения аддитивны, существующие строки не затрагиваются.
2. **Время.** Событие с реальным сеансом — `CONFIRMED`; событие по расписанию без сеанса (`scheduleUnconfirmed`) и место с часами работы —
   `SUGGESTED` (время выбрал движок). `startsAt` пишется у всех, UI в 3b рисует «~» для `SUGGESTED`.
3. **Создание не двигает чужое.** Если активность или место уже есть в плане пользователя (в области видимости семьи) — это конфликт:
   вся операция откатывается с `409 DUPLICATE_ACTIVITY`/`DUPLICATE_PLACE` и списком id, клиент пересобирает день. Автослияния нет.
4. **Один день или выходные — одна транзакция.** Строки `DayScenario` создаются или берутся и блокируются в порядке дат
   (`FOR UPDATE`), ключ идемпотентности проверяется на первой строке группы. Ошибка на любом дне откатывает оба.
5. **Повторное сохранение того же дня** (после «Изменить» в 3b): записи с этим `scenarioId`, которых нет в новом наборе, удаляются,
   остальные обновляются, новые создаются. Ручные записи и записи других сценариев не трогаются (удаление только по `scenarioId`).
   В 3a это поведение закладывается в сервис и покрывается тестом, кнопки «Изменить» в UI ещё нет.
6. **Стоимость.** Запрос сохранения: 1 чтение области видимости семьи, 1 запрос существующих записей на даты, по строке `FOR UPDATE`
   на день, `createMany`-аналог по точкам (до 4 точек × 2 дня), 1 запись `DayScenario` на день. Лимит 10 сохранений в минуту на
   пользователя. Нового чтения каталога нет: данные точек берутся из ответа черновика и проверяются по БД (`PUBLISHED`, существование
   места) одним запросом на тип.
7. **Приватность.** Маршрут требует вход, записи создаются в семье пользователя с видимостью по умолчанию (`FAMILY`); гость сохранить
   не может (до 3c кнопка для гостя ведёт на вход).

## 4. Приёмка 3a

- Миграция применяется на пустой и на заполненной БД без изменения существующих строк; `prisma validate` проходит.
- Сохранение дня создаёт `PlanItem` с `scenarioId/timeType/pinned`, `DayScenario` с `source='ENGINE'` и пересчитанным отпечатком.
- Повтор запроса с тем же ключом отдаёт тот же ответ и не создаёт дублей; тот же ключ с другим телом — 409.
- Дубль активности или места в плане — 409 и **ничего** не записано (в том числе для второго дня выходных).
- Существующие записи плана (ручные, из афиши, на тот же день) не меняются.
- Флаг выключен — маршрут 404 до любой работы с БД.
