# Гео-аудит для движка «Сценария дня» (PR 1, раздел 8 п. 0)

Дата: 2026-11-07 · база `dd88ccf04` · статус: короткий отчёт перед реализацией
BACKLOG-230. Только факты по коду и схеме; решения владельца из раздела 8
основного аудита (`day-scenario-unification-audit-2026-11-07.md`) не пересматриваются.

## 1. Что есть

| Сущность | Гео-поля | Замечание |
|---|---|---|
| `Place` | `lat`, `lng` (`Float?`), `territoryId` (`Territory`: COUNTRY → REGION → CITY), `cityId` | `geoCell*` нет, geohash/индексов нет |
| `Activity` | **собственных координат нет**; `placeId` (→ `Place`), `metroStationId` (→ `MetroStation.lat/lng`), `territoryId` | локация события = `place` либо `venue` |
| `EventVenue` (1:1 с `Activity`) | `lat`, `lng` (собственные), `placeId?`, `addressLine`, `kind` | событие «на чужой площадке» может иметь координаты **в venue**, а не в `Place` |
| `MetroStation` | `lat`, `lng` (обязательные) | годится как приближение «примерное место» |
| `ActivitySession` | только `startsAt` (+ `withdrawnAt`); **длительности нет** | `endsAt`/`durationMinutes` у `PlanItem`, не у сеанса |
| `District` | не связан ни с `Place`, ни с `Activity` | по решению владельца **не используется** |

Источник координат события, в порядке приоритета: `place` → `venue.place` →
`venue.lat/lng` → станция метро (только для «Машина», с признаком
«примерное место») → нет координат (исключается из «Пешком»).

## 2. Расчёты расстояний

- `src/lib/geo/haversineMeters.ts` — каноническая функция (используется в
  `enrich-location`, `PlaceLocationPicker`, `listNearbyCities`, import matcher).
- `src/features/my-plan/lib/scenarioTravel.ts` содержит **собственную копию**
  haversine в км (`haversineKm`) и оценку `estimateTravelMinutes` (24 км/ч,
  минимум 5 мин, округление до 5). Дубль — при расширении переводим на
  `haversineMeters`, оценку времени обобщаем по режимам.
- geohash и гео-индексов в репозитории и БД нет.

## 3. Пути записи `Place.lat/lng`

Более 25 мест вызывают `place.create/update/upsert` (бизнес-визард и API,
`placeRevision`, импорт, миграционный `PlaceCommitWriter`,
`resolvePendingLocationOnPublish`, `placeGeoEnrichment`, `placeLocation`,
иерархия, seed). Поэтому `geoCell6/geoCell5` проставляются **одним Prisma
query-расширением на модель `Place`** (при `create`/`update`/`upsert`/`updateMany`,
если в `data` есть `lat`/`lng`), а не правкой каждого вызова. Расширение
подключается рядом с существующим `extendPrismaWithSearchIndexing`; записи через
голый `prismaBase` (только смена статуса модерации) координат не меняют.
Сохранённые ячейки — только оптимизация и задел под DB-запросы по радиусу;
**движок им не доверяет** (см. п. 4.6): при загрузке пула он всегда считает
`geoCell6/geoCell5` из `lat/lng` и лишь сверяет их с колонками. Идемпотентный
скрипт бэкфилла с режимом `--check` приводит колонки в порядок, но корректность
сценария от него не зависит.

## 4. Решения PR 1 по итогам аудита

1. **`Place.geoCell6` / `Place.geoCell5`** — две nullable-колонки без индексов
   (запросов по ячейкам в БД нет: пул фильтруется в памяти; индекс добавим, когда
   появится DB-запрос по радиусу). Бэкфилл — скрипт, не SQL: geohash в чистом SQL
   без PostGIS хрупок.
2. **`Activity` колонок не получает** (решение владельца): ячейки события
   берутся через `place`/`venue`; для `venue.lat/lng` и метро ячейки считаются в
   памяти при загрузке пула (микросекунды, на уровне TTL-кэша).
3. **Уточнение к «TravelEstimate»:** на haversine таблица в Postgres не даёт
   выигрыша — расчёт пары стоит микросекунды, а запрос в БД — миллисекунды, и
   кэш производных от координат значений устаревает при переносе `Place`. В PR 1
   `TravelEstimate` реализован как **in-memory кэш пар** `(from, to, mode)` с тем
   же TTL, что у пула, за интерфейсом, который позже можно подменить таблицей при
   подключении реального роутинга. Таблица откладывается (BACKLOG-233).
4. **Длительность события** в данных не хранится → константа
   `DEFAULT_EVENT_DURATION_MIN = 90` (настраиваемая), для сеансов с известным
   `PlanItem.endsAt` используется он. Это допущение, не измерение.
5. **Существующие записи плана** на дату (активности, места, заметки с
   временем) становятся «занятыми интервалами»: события из них исключаются из
   пула, остальные точки строятся вокруг.
6. **Устаревшие ячейки (вариант «а»):** пул не доверяет сохранённым колонкам —
   `geoCell6/5` вычисляются из `lat/lng` при каждой загрузке пула (микросекунды
   на ≤200 строк внутри TTL-кэша), колонки сверяются, расхождение пересчитывается
   в памяти и пишется в лог со счётчиком `staleGeoCells`. Выбран вместо
   обязательного `--apply` после включения флага: нет ручных шагов и нет окна,
   в котором сценарий может опираться на устаревшую ячейку.
7. **Фича-флаг:** серверный `DAY_SCENARIO_ENGINE_ENABLED=true`, по умолчанию
   выключен на всех окружениях (паттерн `PARTY_CONFIRMATION_ENABLED`); маршрут
   при выключенном флаге отвечает 404 и не делает запросов к БД.
8. **Не входит в PR 1:** `DayScenario.groupId`, `PlanItem.scenarioId/pinned`,
   поле режима передвижения в профиле семьи — аддитивные колонки появятся в
   PR 2–3, где их читает UI/сохранение (движок и типы уже учитывают `pinned`,
   диапазон и режим). Квота гостя «первая сборка на дату» тоже в PR 2–3.

## 5. Риски

- Пул per-instance (in-memory): «0 запросов к БД при пересборке» верно на
  инстанс в пределах TTL; после рестарта первая сборка идёт в БД.
- Устаревшие ячейки: пока флаг выключен (или запись шла мимо расширения: сырой
  SQL, `prismaBase`), у места с уже проставленными `geoCell6/5` могут поменять
  `lat/lng`, и колонки останутся старыми. Это **не влияет на сценарий**: пул
  всегда считает ячейки из `lat/lng` (вариант «а»), а расхождение с колонками
  даёт предупреждение `[day-scenario-pool]` со счётчиком `staleGeoCells` (он же в
  `meta` ответа). Колонки исправляет `backfill:place-geo-cells -- --apply`,
  когда удобно; ручной шаг после включения флага не требуется.

## 6. Что вошло в PR 1 и порядок выкатки

Вошло: `Place.geoCell6/geoCell5` + расширение Prisma + скрипт бэкфилла; чистый
движок `buildDayScenario` (режимы walk/car/transit, anchors/pinned, variant,
replace) и in-memory `TravelEstimator`; загрузчик пула и TTL-кэш 10 мин;
`POST /api/plan/day-scenario/draft` за флагом `DAY_SCENARIO_ENGINE_ENABLED`
(по умолчанию выключен, 404 без запросов к БД). Записей в БД маршрут не делает.

Порядок на окружении (DEV → потом PROD по релизной процедуре):
1. деплой образа (флаг выключен — поведение не меняется);
2. `prisma migrate deploy` (аддитивные nullable-колонки `Place.geoCell6/geoCell5`);
3. включить `DAY_SCENARIO_ENGINE_ENABLED=true` только на окружении замера
   (расширение `Place` тоже за этим флагом: пока он выключен, любая запись `Place`
   проходит без изменений — зона RC1 не затронута);
4. по желанию `pnpm backfill:place-geo-cells -- --apply`, затем `--check`
   (ожидаем exit 0) — гигиена колонок, не условие корректности: движок считает
   ячейки из `lat/lng` всегда.

Не вошло (осознанно): UI, сохранение, `groupId`, квота гостя, профиль режима
передвижения, персистентная таблица `TravelEstimate` (BACKLOG-233),
`resolveSelectedExperienceAffinity` в скоринге сценария (скоринг = engagement +
интересы профиля; опыт семьи добавим вместе с UI).

Локальные измерения (БД с 1 событием на дату без координат — только структура):
холодный пул — 8 запросов к БД, тёплый пул (повторная сборка, «Другой вариант»,
«Заменить», смена режима) — **0 запросов** к пулу; маршрут дополнительно тратит
1 запрос на rate limit и, для залогиненного, запросы сессии/плана/персон.

## 7. PR 1b — места-заполнители в движке (за тем же флагом)

Пул = подтверждённые сеансы событий + опубликованные `Place` с координатами
(`getPublicPublishedPlaceWhere`, территория Минска и области, до 400 мест). Места
не идут через сеансы: старт выбирается на сетке 30 минут внутри окна дня и часов
работы.

Правила часов работы (`openingHours.ts`, на дату сценария):

| Состояние места | Поведение |
|---|---|
| `WEEKLY` с правилом дня | окна из интервалов; исключение на дату перекрывает правило (закрыто / весь день / свои интервалы) |
| `WEEKLY` без открытого правила на этот день | исключается |
| `ALWAYS_OPEN` | всегда открыто |
| `BY_APPOINTMENT`, `TEMPORARILY_CLOSED` | исключаются |
| нет записи часов | допускается, `hoursUnconfirmed=true` («уточните часы работы»), полезность ниже на 8 пунктов |

Остальное (все значения в `fillers.ts`, не в коде сборщика):
- длительность по умолчанию 90 мин, «Кафе и еда» (slug `food` или имя) — 60 мин;
- места без основной категории участвуют, но **не больше одного на сценарий**
  (закреплённое такое место тоже занимает единственный слот);
- полезность: событие 25–100 (отношение балла к лучшему), заполнитель 18 (10 без
  часов): событие с нулевым engagement всё равно выше заполнителя;
- место, уже стоящее в плане пользователя на дату (`PlanItem.placeId`), не
  предлагается;
- ответ маршрута: у пункта `kind` (`event`/`place`) и `hoursUnconfirmed`, в `meta`
  — `poolPlaces`.

Локальный замер на синтетическом наборе формы PROD (120 мест: 114 с координатами,
41 без записи часов, 55 `WEEKLY`, 12 `ALWAYS_OPEN`, 6 + 6 «по записи»/«закрыто»;
87 % без категории; гауссово облако вокруг центра Минска):

| Что | Результат |
|---|---|
| В пул попало | 102 места (114 − 12 исключённых): 12 всегда открыты, 35 без часов, 55 с окнами; 89 без категории |
| Холодная загрузка пула (события + места + часы) | 15 запросов к БД, 48.5 мс локально; пул ≈ 66 КБ |
| Сборка `car` / пересборка / `transit` | p50 ≈ 1 мс, p95 ≤ 3.3 мс |
| Сборка на 480 местах (верхняя граница) | p50 ≈ 2.3–2.6 мс, p95 ≤ 4.6 мс |
| «Пешком» | 1 пункт и `few_nearby` + подсказка про машину |

Вывод по замеру: из-за «не больше одного места без категории» при 87 % мест без
категории пеший сценарий почти не наполняется (категоризировано ~13 % мест) — это
прямое следствие данных, а не ошибка движка (BACKLOG-234).
