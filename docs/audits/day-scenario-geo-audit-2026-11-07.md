# Гео-аудит для движка «Сценария дня» (PR 1, раздел 8 п. 0)

Дата: 2026-11-07 · база `dd88ccf04` · статус: короткий отчёт перед реализацией
BACKLOG-230. Только факты по коду и схеме; решения владельца из раздела 8
основного аудита (`day-scenario-unification-audit-2026-11-07.md`) не пересматриваются.

## 1. Что есть

| Сущность | Гео-поля | Замечание |
|---|---|---|
| `Place` | `lat`, `lng` (`Float?`), `territoryId` (`Territory`: COUNTRY → REGION → CITY), `cityId` | `geoCell*` нет, geohash/индексов нет |
| `Activity` | **собственных координат нет**; `placeId` (→ `Place`), `metroStationId` (→ `MetroStation.lat/lng`), `territoryId` | локация события = `place` либо `venue` |
| `EventVenue` (1:1 с `Activity`) | `lat`, `lng` (собственные), `placeId?`, `addressLine`, `kind` | событие «на чужой площадке» может иметь координаты **в venue**, а не в `Place` |
| `MetroStation` | `lat`, `lng` (обязательные) | годится как приближение «примерное место» |
| `ActivitySession` | только `startsAt` (+ `withdrawnAt`); **длительности нет** | `endsAt`/`durationMinutes` у `PlanItem`, не у сеанса |
| `District` | не связан ни с `Place`, ни с `Activity` | по решению владельца **не используется** |

Источник координат события, в порядке приоритета: `place` → `venue.place` →
`venue.lat/lng` → станция метро (только для «Машина», с признаком
«примерное место») → нет координат (исключается из «Пешком»).

## 2. Расчёты расстояний

- `src/lib/geo/haversineMeters.ts` — каноническая функция (используется в
  `enrich-location`, `PlaceLocationPicker`, `listNearbyCities`, import matcher).
- `src/features/my-plan/lib/scenarioTravel.ts` содержит **собственную копию**
  haversine в км (`haversineKm`) и оценку `estimateTravelMinutes` (24 км/ч,
  минимум 5 мин, округление до 5). Дубль — при расширении переводим на
  `haversineMeters`, оценку времени обобщаем по режимам.
- geohash и гео-индексов в репозитории и БД нет.

## 3. Пути записи `Place.lat/lng`

Более 25 мест вызывают `place.create/update/upsert` (бизнес-визард и API,
`placeRevision`, импорт, миграционный `PlaceCommitWriter`,
`resolvePendingLocationOnPublish`, `placeGeoEnrichment`, `placeLocation`,
иерархия, seed). Поэтому `geoCell6/geoCell5` проставляются **одним Prisma
query-расширением на модель `Place`** (при `create`/`update`/`upsert`/`updateMany`,
если в `data` есть `lat`/`lng`), а не правкой каждого вызова. Расширение
подключается рядом с существующим `extendPrismaWithSearchIndexing`; записи через
голый `prismaBase` (только смена статуса модерации) координат не меняют.
Дрейф ловит идемпотентный скрипт бэкфилла с режимом `--check`.

## 4. Решения PR 1 по итогам аудита

1. **`Place.geoCell6` / `Place.geoCell5`** — две nullable-колонки без индексов
   (запросов по ячейкам в БД нет: пул фильтруется в памяти; индекс добавим, когда
   появится DB-запрос по радиусу). Бэкфилл — скрипт, не SQL: geohash в чистом SQL
   без PostGIS хрупок.
2. **`Activity` колонок не получает** (решение владельца): ячейки события
   берутся через `place`/`venue`; для `venue.lat/lng` и метро ячейки считаются в
   памяти при загрузке пула (микросекунды, на уровне TTL-кэша).
3. **Уточнение к «TravelEstimate»:** на haversine таблица в Postgres не даёт
   выигрыша — расчёт пары стоит микросекунды, а запрос в БД — миллисекунды, и
   кэш производных от координат значений устаревает при переносе `Place`. В PR 1
   `TravelEstimate` реализован как **in-memory кэш пар** `(from, to, mode)` с тем
   же TTL, что у пула, за интерфейсом, который позже можно подменить таблицей при
   подключении реального роутинга. Таблица откладывается (BACKLOG-233).
4. **Длительность события** в данных не хранится → константа
   `DEFAULT_EVENT_DURATION_MIN = 90` (настраиваемая), для сеансов с известным
   `PlanItem.endsAt` используется он. Это допущение, не измерение.
5. **Существующие записи плана** на дату (активности, места, заметки с
   временем) становятся «занятыми интервалами»: события из них исключаются из
   пула, остальные точки строятся вокруг.
6. **Фича-флаг:** серверный `DAY_SCENARIO_ENGINE_ENABLED=true`, по умолчанию
   выключен на всех окружениях (паттерн `PARTY_CONFIRMATION_ENABLED`); маршрут
   при выключенном флаге отвечает 404 и не делает запросов к БД.
7. **Не входит в PR 1:** `DayScenario.groupId`, `PlanItem.scenarioId/pinned`,
   поле режима передвижения в профиле семьи — аддитивные колонки появятся в
   PR 2–3, где их читает UI/сохранение (движок и типы уже учитывают `pinned`,
   диапазон и режим). Квота гостя «первая сборка на дату» тоже в PR 2–3.

## 5. Риски

- Пул per-instance (in-memory): «0 запросов к БД при пересборке» верно на
  инстанс в пределах TTL; после рестарта первая сборка идёт в БД.
- `geoCell*` у `Place`, записанных мимо расширения (сырой SQL, будущие
  импортёры на `prismaBase`), будут `NULL` → пул вычисляет ячейку из `lat/lng`
  на лету, поэтому дрейф не ломает сборку, а только оставляет колонки
  неполными до `--check`/бэкфилла.
