# ABWS Фаза 1 — техзадание

Основано на: аудите импорт-пайплайна (ImportSource/ImportRun/ImportedRecord/
ImportReviewTask, ActivitySession, EventVenue, AgePolicy, UserEvent.CTA_CLICK)
и реальной фикстуре `webgate.24guru.by/api/v3/sync/data/performances`,
818 мероприятий / 8167 сеансов, снята 11.09.2026.

Статус входных данных: подтверждено собственным запросом. Единицы цены на
уровне сеанса (копейки) — выведены логически из диапазона значений, не
подтверждены разработчиком письмом. Не публиковать цену без этого
подтверждения либо без ручной проверки на 10–15 живых карточках.

## 0. Периметр Фазы 1

**Включено:** мероприятия, у которых все сеансы принадлежат одной площадке
(`session.object.id` не меняется внутри мероприятия). По снятой фикстуре —
747 из 818 (91.3%).

**Исключено, откладывается на Фазу 2:** мероприятия с сеансами на разных
площадках — 71 из 818, но с непропорционально большим числом сеансов
(пример: «Край чудес» 253 сеанса/41 площадка, «Лунтик» 110/19). В основном
кино. Эти мероприятия импортируются в `RawItem`/`ImportedRecord`, но
**не публикуются** — статус `pendingMultiVenue`, чтобы не терять данные и не
парсить дважды при переходе к Фазе 2.

Критерий разделения — единственная новая функция в адаптере:

```ts
function isSingleVenue(sessions: AbwsSession[]): boolean {
  const venueIds = new Set(sessions.map(s => s.object?.id).filter(Boolean));
  return venueIds.size <= 1;
}
```

## 1. Источник и синхронизация

```
GET https://webgate.24guru.by/api/v3/sync/data/performances
    ?key={ABWS_KEY}
    &distributor_company_id=550
```

Подтверждено вручную: `lastSync` в этот вызов не передавался, сервер вернул
полный каталог (818/8167, 13 МБ, ~20 сек). Не подтверждено, принимает ли
`v3` параметр `lastSync` вообще — в вики он документирован для `performances`,
но не проверен нами на этом хосте. Не полагаться на него, пока разработчик
не подтвердит явно.

Практическое следствие: инкремент строим на своей стороне, не на `lastSync`.

- Полный запрос раз в час (значение по умолчанию из вики; 10–20 минут —
  только по согласованию, которого у нас нет).
- Сравнение по `contentHash` на уровне `ImportedRecord`, как уже сделано для
  family.by. Хешировать `performance` и весь массив `sessions` вместе —
  если поменялась хоть одна дата/цена сеанса, запись обновлять.
- Если производительность на 818 записях/13 МБ раз в час станет проблемой —
  оптимизировать позже, сейчас объём не оправдывает усложнение.

Соблюдать рекомендации вики дословно:
- логировать HTTP-код и тело ответа на каждый вызов;
- lastSync/курсор обновлять только после успешного ответа;
- при ошибке — ретрай не чаще раза в 30–60 секунд, без агрессивных повторов;
- переиспользовать advisory lock на запуск (уже есть в пайплайне — баг из
  Фазы 0, но если Фаза 0 ещё не сделана, для ABWS он обязателен с первого
  дня, т.к. часовой вызов почти гарантированно наложится на ручной перезапуск).

## 2. Модель данных — миграции

### 2.1 Источник

```prisma
// ImportSource, если ещё не создан
{
  id: "abws"
  name: "24afisha.by (ABWS)"
  baseUrl: "https://webgate.24guru.by/api/v3"
}
```

### 2.2 Идентичность сеанса (обязательно, даже для одноплощадочных)

Из аудита: `ActivitySession { id, activityId, startsAt }` — минимальная
модель без внешнего ключа и без состояния. Расширить:

```prisma
model ActivitySession {
  id          String   @id @default(cuid())
  activityId  String
  startsAt    DateTime

  // новое:
  source        String?   // "abws" | null для собственных сеансов
  externalId    String?   // ABWS session.id, напр. "1743171"
  buyUrl        String?   // session.urlSaleframe
  priceMinCents Int?      // session.minPrice, копейки как есть
  priceMaxCents Int?      // session.maxPrice
  isSaleOpen    Boolean?  // session.isSaleOpen
  withdrawnAt   DateTime? // из session.deletedAt, если не null

  @@unique([source, externalId])
}
```

`@@unique([source, externalId])` — без него повторный импорт создаст дубли
сеансов при каждом запуске. Это тот же класс бага, что был найден в аудите
на уровне `ImportedRecord`, здесь он же на уровень ниже.

### 2.3 Площадка (для Фазы 1 — одна на мероприятие)

`EventVenue.activityId @unique` из аудита остаётся как есть — Фаза 1 не
трогает эту связь. Площадка заполняется из `sessions[0].object` (для
одноплощадочных мероприятий все `object` идентичны, брать первый).

Добавить внешний ключ на Place для матчинга:

```prisma
model Place {
  // ...существующие поля
  source     String?
  externalId String? // ABWS object.id
  @@unique([source, externalId])
}
```

Матчинг при первом импорте: `(source="abws", externalId=object.id)` →
если не найдено, искать по `(name, city.slug)` нестрого (contains,
без учёта регистра) → если не найдено, создавать `needsPlaceMapping=true`,
Place не создавать автоматически, событие уходит в `ImportReviewTask`.

### 2.4 Цена мероприятия

`performance.minPrice`/`maxPrice` — строка, рубли с двумя знаками
(`"34.00"`). `session.minPrice`/`maxPrice` — число, копейки (не подтверждено
письмом, выведено из диапазона). Хранить оба уровня раздельно, не сводить
одной функцией конвертации:

```ts
const perfPriceRub = parseFloat(performance.minPrice); // уже рубли
const sessionPriceRub = session.minPrice / 100;          // гипотеза: копейки
```

На карточке показывать `sessionPriceRub`, если у мероприятия есть сеансы
(всегда для ABWS), `perfPriceRub` — fallback, если сеансов почему-то нет.

## 3. Контракт адаптера

Реализует существующий интерфейс `EventImportParser` (наследует `ImportParser`
из `src/server/modules/import/parsers/base.parser.ts`). Контракт минимален —
**только** `parserKey` и `parse(source)`:

```ts
export interface ImportParser {
  readonly parserKey: string;
  parse(source: ImportSource): Promise<ParserResult>;
}
```

`ParserResult` — плоский список `ParsedRawRecord` (`externalId`, `sourceUrl`,
`rawPayload`, `sourceUpdatedAt`, …). Конвейер (`import-pipeline.service.ts`)
вызывает у парсера только `parse()` — нормализация (`normalizeRunRecords`) и
матчинг (`matchRunRecords`) идут отдельными проходами по уже сохранённым
`ImportedRecord`, а не через методы адаптера. Класс с публичными методами
`fetchRaw/normalize/reconcile` (как в предыдущей редакции этого раздела) не
типизируется как `ImportParser` и, даже если бы типизировался, эти методы
пайплайн никогда не вызвал бы — по аналогии с `family-by-afisha-event.parser.ts`,
где вся полевая маппинг-логика идёт через `rawPayload`, а не через методы
класса-парсера.

Правильная форма — один файл `abws-performances-event.parser.ts`:

```ts
export const abwsPerformancesEventParser: EventImportParser = {
  parserKey: "abws-performances-event",
  entityType: "EVENT",

  async parse(source) {
    // один HTTP-вызов (раздел 1), без lastSync, с логированием кода/тела
    const items = await fetchAbwsPerformances(source);

    return {
      parserKey: "abws-performances-event",
      totalFound: items.length,
      records: items.map((item) => ({
        externalId: item.performance.id.toString(),
        sourceUrl: item.performance.urlSaleframe,
        rawPayload: {
          performance: item.performance,
          sessions: item.sessions,
          isSingleVenue: isSingleVenue(item.sessions), // раздел 0
        },
      })),
    };
  },
};

function isSingleVenue(sessions: AbwsSession[]): boolean {
  const venueIds = new Set(sessions.map(s => s.object?.id).filter(Boolean));
  return venueIds.size <= 1;
}
```

**Открытый вопрос реализации (уточнить перед кодированием, не перед стартом
Фазы 1):** маппинг полей (раздел 5), LLM-нормализация (раздел 6), матчинг
`Place` (раздел 2.3) и реконсиляция по `deletedAt`/`isSaleOpen` (раздел 4)
у family.by устроены как «сырой `rawPayload` → отдельный apply-слой», но этот
apply-слой сегодня рассчитан на модель мест/событий без вложенных сеансов
(`ActivitySession` с ценой/`buyUrl`/`withdrawnAt` на уровне сеанса — новое
для ABWS, раздел 2.2). Нужно на старте реализации проверить, достаточно ли
существующих `normalizeRunRecords`/`matchRunRecords` для записи сеансов, или
для EVENT-парсеров с сеансами нужен отдельный шаг конвейера — это инженерное
решение при реализации, не блокирует написание миграций/адаптера.

## 4. Реконсиляция — состояния

Три независимых сигнала, не путать между собой:

| Сигнал | Где | Значение |
|---|---|---|
| `performance.deletedAt != null` | мероприятие | снять с публикации целиком |
| `session.deletedAt != null` | сеанс | снять конкретный сеанс, мероприятие живёт если есть другие |
| `session.isSaleOpen == false` | сеанс | не значит отменён. В фикстуре это в основном прошедшие сеансы (дата раньше текущего момента). Скрывать кнопку «Купить» на этом сеансе, но не удалять и не трогать статус мероприятия |

По факту в снятой фикстуре: `performance.deletedAt` — 0 из 818 null. Это
означает только то, что снятых мероприятий не было в этот конкретный
момент, не то, что поле не работает — обрабатывать его в любом случае.
`session.deletedAt` — не null у ~2% сеансов (при живом мероприятии), это
подтверждённый рабочий случай, а не гипотетический — обработка обязательна
с первого дня, а не «добавим потом».

Правило: мероприятие целиком снимается с публикации **только** если у него
`deletedAt != null`. «Ни одного сеанса в будущем» само по себе не повод для
снятия — это обычное прошедшее мероприятие, для него действует правило
раздела 9 (остаётся доступно с пометкой «прошло»). Более ранняя редакция
этого правила добавляла второе условие («ни один сеанс не в будущем И
`isSaleOpen == false` у всех»), которое на практике покрывает тот же самый
случай прошедшего мероприятия и противоречило бы разделу 9 — убрано.
Отдельно снятые сеансы (`session.deletedAt != null`) просто перестают
отображаться в списке дат, статус мероприятия не трогают.

### 5.1 Whitelist категорий из `types[]`

Поле реально смешивает категории событий и названия конкретных площадок
(«Брестский театр драмы» id 54 как «тип» наравне с «Кино» id 1). Прогонять
через хардкод-whitelist, не маппить весь массив:

```ts
const CATEGORY_TYPE_IDS = new Set([1, 2, 3, 15, 16, 17, 22, 29, 41]);
// Кино, Концерты, Театр, Спорт, Цирк, Квесты и квизы, Фестивали,
// Музеи и выставки, Активный отдых — подтверждено по фикстуре

// id вроде 54 (Брестский театр драмы), 45 (Большой театр Беларуси),
// 48 (КЗ "Минск") — площадки, попавшие в types. Игнорировать при маппинге
// категории, площадка и так приходит структурированно через session.object.
```

Список не полный (в фикстуре встретилось 23 из неизвестного общего числа) —
при первом полном импорте залогировать все встреченные `types[].id`, не
попавшие в whitelist, и добавить в справочник по факту, не гадая заранее.

## 6. LLM-нормализация

Один вызов на мероприятие, строго JSON, входные данные —
`name` + `shortDescription` (не полный `description`, короче и чище) +
`minAge` (уже известен, LLM только уточняет верхнюю границу и аудиторию):

```json
{
  "category": "cinema",
  "categoryConfidence": 0.94,
  "categoryAlternatives": [],
  "audience": "family",
  "audienceConfidence": 0.88,
  "ageMax": 12,
  "interests": ["animation", "adventure"],
  "occasions": ["weekend"],
  "description": "переписанный текст, не копия исходного",
  "flags": []
}
```

Правило безопасности по умолчанию: `audienceConfidence < 0.8` →
`audience = adult`, в топ выдачи и на главную не пускать.
`categoryAlternatives` не пуст → публикуется с основной категорией,
попадает в отдельный список в админке для ручного просмотра (не блокирует
публикацию, решено ранее).

## 7. Дедуп с партнёрскими событиями

Ключ — тройное совпадение: нормализованное название + дата первого сеанса +
площадка (`Place.id` после матчинга). При совпадении — не публиковать
автоматически, `ImportReviewTask` на ручное решение (партнёрская карточка
или ABWS с фреймом). Совпадение по одному названию или одному адресу — не
использовать, даёт слишком много ложных срабатываний на одной площадке с
множеством событий.

## 8. Кнопка «Купить» и трекинг

- Ссылка — `session.urlSaleframe` (`?sid=`), не `performance.urlSaleframe`.
  Для одноплощадочных мероприятий с несколькими сеансами показывать список
  дат, каждая — своя ссылка на свой `sid`.
- Клик идёт не напрямую на `saleframe.24afisha.by`, а на внутренний роут.
  **Не** `/n/[id]` — этот путь занят: `src/app/n/[id]/route.ts` уже
  реализует резолвер клика по уведомлению (`id` — это `Notification.id`,
  анонимных редиректит на логин, неизвестный `id` — на `/`), переиспользовать
  его для ABWS-ссылок нельзя, ни `CTA_CLICK` не запишется, ни на sale frame
  не попадёт. Нужен отдельный namespace, например `/go/abws/[sessionId]`
  (`sessionId` = `ActivitySession.externalId`). Роут пишет `UserEvent` с
  типом `CTA_CLICK` (поле уже существует), затем редиректит или открывает
  модалку с фреймом.
- Модалка с fallback на «открыть в новом окне» — обязательно проверить на
  iOS Safari до релиза, платёжные формы в iframe там часто ломаются.
- CSP: добавить `frame-src https://saleframe.24afisha.by` (по аудиту —
  сейчас `frame-src` в проекте не задан, блокировать нечему, но заголовок
  всё равно стоит прописать явно, а не полагаться на отсутствие ограничения).

## 9. Публикация

- Автопубликация сразу после нормализации, с переписанным LLM описанием —
  не с оригинальным текстом источника (SEO-риск near-duplicate, решено ранее).
- Собственный URL по `title` (решено ранее), slug фиксируется при первой
  публикации, не меняется при переименовании на стороне ABWS.
- Многоплощадочные (`pendingMultiVenue`) — не публикуются, не в sitemap,
  ждут Фазы 2.
- Прошедшие мероприятия (все сеансы в прошлом) — остаются доступны с
  пометкой «прошло» (решено ранее), не удаляются.

## 10. Открытые вопросы к разработчику (не блокируют старт)

Можно уточнить одним письмом, когда будет полезно, не срочно:

1. Подтвердить единицы `session.minPrice/maxPrice` — копейки?
2. Работает ли `lastSync` на `v3`/`webgate.24guru.by`, и если да — как

3. Назначение `session.type: "related"` в отличие от `"default"`.
4. Полный справочник `types` с id (мы видим только то, что попало в выборку).
