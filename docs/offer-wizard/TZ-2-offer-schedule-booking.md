# ТЗ 2. Расписание и бронирование офферов

**Зависимость:** PR #526 (`BookingUnit`, `BookingAllocation`, exclusion constraint) смержен. До этого — только дизайн и тесты на ветке поверх #526.
**Не блокирует:** релиз 15.10 и ТЗ 1.
**Источник правды:** этот пакет `docs/offer-wizard/`. Ранний черновик схемы `offer-schedule.prisma` заменён этим ТЗ и в репозиторий не входит; схема бронирования реализована в #532 (`OfferBooking`, `ScheduleKind`, поля `BookingRequest`).

---

## 0. Ограничения (обязательно)

1. PROD не трогать без отдельного разрешения. Миграции аддитивные, с обратной совместимостью.
2. Единый источник доступности для офферов и конструктора праздников: `BookingUnit` + `BookingAllocation`. Вторую систему блокировок не создавать (`BookingUnitLock` из спецификации — отменён).
3. Заявки — через существующий `BookingRequest`. Параллельной модели `Booking` нет.
4. Повторно используем: `BookingUnitOffer`, `AvailabilityRule`, существующие исключения календаря ресурсов, `OfferSession`. Новые модели — только если существующие не покрывают требование; обоснование в PR.
5. Автотесты обязательны (§6).

## 1. Режимы и типы расписания

**`BookingMode`** (существующий enum, расширен в ТЗ 1):

| Значение | Смысл |
|---|---|
| `NONE` | Без записи |
| `REQUEST_ONLY` | По заявке |
| `EXTERNAL` | Внешняя ссылка |
| `USE_PUBLICATION_DATES` | По расписанию: конкретные даты/смены |
| `USE_PUBLICATION_SLOTS` | По расписанию: слоты из правил |

**`ScheduleKind`** (новый enum) — форма расписания; выводится из типа оффера, бизнес его не выбирает:

| Тип оффера | ScheduleKind | Режим | Механизм занятости |
|---|---|---|---|
| PLACE_VISIT | `OPENING_HOURS` | SLOTS (если есть вместимость), иначе NONE | вместимость на интервал (опц.) |
| CLASS, PROGRAM (регулярные) | `RECURRING_SESSIONS` | SLOTS | места в группе |
| CLASS, PROGRAM (разовые) | `DATED_SESSIONS` | DATES | места в группе |
| PARTY_SERVICE, PARTY_PACKAGE | `ON_REQUEST_WINDOWS` | SLOTS | эксклюзивный ресурс |
| CAMP | `SHIFTS` | DATES | места в смене |

## 2. Данные

**`OfferBooking`** (новая, 1:1 к `Offer`, вне `OfferRevision` — правки не требуют модерации):
`offerId @unique`, `scheduleKind?`, `timezone` (default `Europe/Minsk`), `durationMin?`, `bufferMin` (default 0), `capacity?`, `leadTimeHours` (default 24), `horizonDays` (default 60), `externalKind?`, `externalUrl?`.
Если `externalUrl` уже хранится на `Offer` после ТЗ 1 — не дублировать, перенести одной миграцией с бэкфиллом.

**Повторяющиеся правила оффера** (`RECURRING_SESSIONS`, `OPENING_HOURS`):
сначала проверить, покрывает ли `AvailabilityRule` правила оффера (weekdays, startMin/endMin в локальном времени, validFrom/To, capacity). Если да — переиспользовать с привязкой к офферу; если нет — `OfferScheduleRule` с теми же полями. Для `ON_REQUEST_WINDOWS` окна берутся из `AvailabilityRule` ресурсов, а не из оффера.

**Датированные сеансы и смены:** `OfferSession` (`startsAt`, `endsAt`, `capacity`, `title`, `isCancelled`).

**Смены лагеря** (тот же `OfferSession`, тип `SHIFT`, или отдельная `CampShift` — по результату проверки `OfferSession`):
- `title` * — название смены
- `dateFrom` *, `dateTo` * — один выбор диапазона в календаре; **продолжительность не вводится**, считается: дни = `dateTo − dateFrom + 1`, для выездного лагеря дополнительно ночи = дни − 1
- `price` * — цена за смену за ребёнка (цена услуги «путёвка» — значение по умолчанию)
- `capacity` — мест
- `program` — программа смены (текст)
- `includes` — что входит в стоимость (текст)
- `baseLocation` — локация базы (адрес/название); у разных смен может отличаться
- для родителя: выбор смены в карточке показывает название, даты, продолжительность, базу, программу и «что входит»; цена = `price × детей` с применением акций

**Исключения:** закрытые дни ресурса — существующий механизм. Для офферов без ресурсов (группы) — исключение на уровне `OfferBooking`, если существующий механизм не привязывается к офферу.

## 2a. Услуги (модули) и правило цены

**Терминология:** в интерфейсе и текстах для бизнеса и родителей — только «услуга» («Добавить услугу», «Состав пакета: 4 услуги»). Слово «модуль» в UI не используется. В коде — `OfferModule`, чтобы не путать с типом оффера `PARTY_SERVICE`.

**Название услуги** редактируется в карточке услуги, в блоке «Основное», вместе с полем «Кто или что занято» (ресурс). Новая услуга создаётся с пустым названием, фокус сразу ставится в это поле; без названия шаг не проходит.

Решение: оффер состоит из **модулей**. Модуль — переиспользуемая единица продажи бизнеса из его библиотеки. Один модуль (например «Аниматор Маша») участвует в нескольких пакетах и в конструкторе праздников; цена, время, занятость и промо меняются в одном месте. Простой оффер (занятие, аренда площадки, смена лагеря) — это оффер из одного модуля; в UI слово «модуль» тогда не показывается.

Перед проектированием проверить, чем в PR #526/#529 являются `PartyOrderItem` и услуги конструктора: если там уже есть сущность «услуга бизнеса» — модуль строится на ней, а не рядом.

**`OfferModule`** (библиотека бизнеса, `partnerId`):
- `name` *, `description` (до 200 символов — родители видят в составе пакета и среди доп. услуг), `photos` (до 5, первое — обложка; через существующий media-пайплайн с SHA-256 дедупликацией и `MediaUsage`)
- время: `durationType` (`NONE` | `FIXED` | `MIN_PLUS_STEP`), `durationMin`, `stepMin`, `stretchesWithOrder` (bool — тянется за длительностью заказа, как зал)
- цена (одно правило для всех форматов):
  - `priceBasis` (`ORDER` | `CHILD`)
  - `basePrice` — за минимум / за заказ / за ребёнка
  - `extraStepPrice` — за каждый шаг сверх минимума (скидка за последующие часы задаётся тем, что ставка ниже базовой)
  - `guestsIncluded`, `pricePerExtraGuest`, `maxGuests`
- промо — список `ServicePromo` (см. ниже, до 3 на услугу)
- связь с ресурсами: `BookingUnitOffer` → `BookingModuleUnit` (модуль занимает зал/аниматора на свою длительность)
- модерацию проходят только тексты и фото модуля; цена, время, промо — операционные данные, без `OfferRevision`.

**`ServicePromo`** (акция на услугу):
- `moduleId`
- `type`: `PERCENT` | `AMOUNT` | `GIFT`; `value` (для % и BYN), `giftText` (для подарка)
- `appliesBy`: `VISIT_DATE` (дата праздника/визита) | `BOOKING_DATE` (раннее бронирование)
- для `VISIT_DATE`: `weekdays Int[]` (1–7 ISO), `timeFromMin?`, `timeToMin?` (локальное время, интервал `[from, to)`, проверяется время начала)
- `dateFrom?`, `dateTo?` (включительно; для `BOOKING_DATE` — даты, когда бронируют)
- `isActive`

Правила применения:
- к каждой услуге применяется **одна** — самая выгодная подходящая — денежная акция; акции не суммируются;
- подарки (`GIFT`) не меняют цену, показываются строкой в карточке и в заявке;
- в празднике скидка считается от цены услуги в празднике (+ её доплаты за время и гостей);
- `AMOUNT` не может превышать долю услуги;
- в карточке родителя неподошедшие акции показываются подсказкой с условиями («−10%: будни 15:00–17:00»), чтобы мама могла выбрать подходящее время;
- сработавшие акции сохраняются в снимке заявки вместе с ценой.

Эталон для тестов: праздник 350, зал −10% в будни 15:00–17:00, слот Пт 15:00 → −17 BYN (от 170) → итого 333; без аниматора → 243. Слот Сб 10:00 → 350, подсказка с условиями акции.

**«Мои услуги» — единая база.** Услуга создаётся один раз и используется: как отдельное предложение (`PARTY_SERVICE` с одной услугой, тексты и фото берутся из услуги), в праздниках под ключ, в конструкторе. В карточке услуги в кабинете видно, где она используется. При изменении общих полей — плашка «Изменится в N местах»; удаление услуги, которая есть в праздниках, — только с подтверждением.

**`OfferModuleItem`** (услуга внутри праздника):
- `offerId`, `moduleId`, `sort`
- `role`: `REQUIRED` | `INCLUDED_REMOVABLE` | `OPTIONAL`
- `durationInPackage?` — время услуги в этом празднике (мин); пусто → `durationMin` услуги
- `noteInPackage?` — комментарий для этого праздника (родители видят вместо описания услуги)
- `priceInPackage?` — **цена этой услуги в этом празднике** (за минимум / за заказ / за ребёнка — в той же единице, что `basePrice`). Пусто → берётся `basePrice` услуги. Обычно ниже отдельной цены.

Граница общего и своего:
| Общее для услуги (меняется везде) | Своё в празднике |
|---|---|
| название, описание, фото, правило продления и гостей, промо, ресурс; время и цена по умолчанию | роль, `priceInPackage`, `durationInPackage`, `noteInPackage`, порядок |

**UX состава праздника (обязательно):**
- Услуга, добавленная из «Моих услуг», появляется **свёрнутой одной строкой**: обложка, название, время и ресурс, роль (чип), цена в празднике (и зачёркнутая отдельная, если ниже), кнопка «Изменить», ✕. Строка подсвечивается и показывает «Добавлено из „Моих услуг“…».
- «Изменить» раскрывает два блока:
  1. **«Только в этом празднике»** — роль, цена, время, комментарий. Изменённые поля помечаются «изменено для праздника · вернуть: <значение из базы>». В свёрнутой строке — «своё: цена, время…».
  2. **«Общие данные услуги»** — карточка-сводка из базы и кнопка «Редактировать в базе». Полный редактор открывается только по ней, с предупреждением «Изменения применятся во всех местах: N предложений и конструктор».
- «Создать новую услугу» открывает сразу полный редактор (данных ещё нет) и сохраняет услугу в «Мои услуги».

**Цены пакета как отдельного поля нет.** Цена праздника = Σ `priceInPackage` обязательных и включённых услуг. Убрал услугу — минус ровно её цена в празднике. Добавил доп. услугу — плюс её цена в празднике. Поля `packagePrice` и `removeMode` из предыдущей версии ТЗ — **отменены**.

**Расчёт цены — одна чистая функция `quoteOffer(offer, {durationMin, guests, removed[], added[], when})`:**
```
modulePrice(m, base, dur, guests) =
  CHILD: base × max(1, guests)
  ORDER: base
       + ceil(max(0, dur − durationMin) / stepMin) × extraStepPrice
       + max(0, guests − guestsIncluded) × pricePerExtraGuest

Отдельная услуга: total = modulePrice(m, m.basePrice, dur, guests)

Праздник:
  pb(x) = x.priceInPackage ?? m.basePrice
  total = Σ modulePrice(m, pb(x), dur(m), guests)   по REQUIRED и INCLUDED_REMOVABLE, кроме removed
        + Σ modulePrice(m, pb(x), m.durationMin, guests) по added OPTIONAL
  dur(m) = stretchesWithOrder ? выбранная длительность : m.durationMin
  separate = то же, но с m.basePrice вместо pb(x)  → показывается как «отдельно» и «выгода»
  затем акции (см. ServicePromo) на сумму каждой услуги
```
Эталонные примеры для тестов (должны совпасть до рубля). Праздник «В джунглях»: зал 200 → в празднике 170, аниматор 120 → 90, шоу 60 → 40, торт 80 → 50; фотограф (по желанию) 90 → 70; включено 10 детей, зал +70/час, +12/ребёнок.
| Сценарий | Итог | Отдельно |
|---|---|---|
| Зал отдельно: 3 ч, 14 детей | 318 | — |
| Праздник, суббота | 350 | 460 |
| Праздник, суббота, без аниматора | 260 | 340 |
| Праздник, суббота, без аниматора, 3 ч, 14 детей | 378 | 458 |
| Праздник, суббота, + фотограф | 420 | 550 |
| Занятие 25 BYN/ребёнок, 3 ребёнка | 75 | — |

`quoteOffer` используется в трёх местах одинаково: превью в мастере, карточка для родителя, сумма в `BookingRequest`/заказе (сохраняется снимком на момент заявки, вместе с составом).

**Занятость пакета:** при брони каждый модуль с ресурсом создаёт `BookingAllocation` на своё время внутри слота (`stretchesWithOrder` — на всю длительность, остальные — на свою `durationMin`, по умолчанию с начала слота). Убранный модуль allocation не создаёт. Слот доступен, только если свободны ресурсы всех оставшихся модулей.

**Мастер:** шаги «Расписание» и «Цена» объединены в шаг «Запись и цены»: режим записи → список модулей (карточка модуля: Время · Цена · Запись · Промо) → для праздника у каждой услуги строка «Цена в этом празднике / отдельно / −N%» и итог «В празднике · Отдельно · Выгода семьи». Предоплата, отмена и контакты — шаг «Условия и контакты». Прототип: артефакт «Мастер предложений mamaGo», v2.

## 2b. Шаг «Расписание» в мастере; брони — в Календаре кабинета

**Расписание задаётся в мастере** — отдельный шаг 4 (после «Услуги и цены»), обязательный для любого предложения. **Контроль броней и заявок** (подтвердить, отклонить, закрыть отдельные часы, ручная запись) — в существующем Календаре кабинета. Оба читают и пишут одни и те же данные; параллельную модель часов работы не создавать (фаза 0 показывает, на какие таблицы текущего Календаря это ложится).

Шаги мастера: 1 Что предлагаете · 2 О предложении · 3 Услуги и цены · **4 Расписание** · 5 Условия и контакты · 6 Проверка.

Шаг «Расписание» — 3–4 пронумерованных блока, только нужные для формата:
1. **Когда работаете** (зависит от формата):
   - праздник, место: дни (кнопки Пн–Вс + пресеты «Каждый день / Будни / Выходные») и **одно** время «с–до». Ссылка «В разные дни разное время» раскрывает построчный режим;
   - занятия регулярные: «время занятия» = дни + начало + мест в группе (несколько строк); разовые — список дат;
   - лагерь: смены (название, даты одним полем, вычисляемая продолжительность, цена, места, программа, что входит, база).
2. **Выходные и особые дни** — календарь месяца, клик закрывает/открывает день; закрытые дни списком чипов. (Нет у лагеря.)
3. **Как к вам записываются** — 4 карточки: Без записи · По заявке · Онлайн-запись · Своя ссылка. Для онлайн-записи праздников и мест — выбор из двух карточек: «Готовые слоты» (`FIXED_SESSIONS`) или «Родитель выбирает длительность» (`FLEXIBLE_START`), плюс «Уборка между» и «Бронь не позднее чем за». Шаг начала по умолчанию 30 мин (в «Дополнительно» на будущее).
4. **Так увидят родители** — 2 недели (закрытые дни помечены «закрыто») и **полоса дня**: рабочее окно с часовой шкалой, блоки слотов, штриховкой — уборка. Для FLEXIBLE_START — чипы длительности и список возможных стартов.

Внизу шага: «Брони, заявки и закрытие отдельных часов — в Календаре кабинета».

Режим записи и ссылка переезжают с шага цен на этот шаг. В карточке услуги вместо расписания — подсказка «Когда работаете и как записываются — на шаге „Расписание“».

**Алгоритм `getStartTimes(offerId, date, durationMin)`** (заменяет `getSlots` для праздников и аренды):
1. Окна дня = часы работы всех ресурсов, нужных услугам предложения, минус закрытое время, минус активные allocation (каждая с её уборкой).
2. `FIXED_SESSIONS`: старты = open, open + (dur + buffer), … — длительность одна, выбора длительности у родителя нет.
3. `FLEXIBLE_START`: кандидаты каждые `startStepMin` внутри свободного окна `[a, b)`, где `t + dur ≤ b`. Кандидат показывается, только если не оставляет непродаваемых окон:
   - до: `t − a == 0` или `t − a ≥ minDur + buffer`;
   - после: `t + dur + buffer ≥ b` или `b − (t + dur + buffer) ≥ minDur`.
4. `leadTime`, `horizon`, затем проверка ресурсов по правилам «И» / «ИЛИ» (§2c, «Ресурсы: И и ИЛИ»). Для «И» (зал + аниматор — разные услуги праздника) старт со всеми свободными ресурсами — `FULL`; если свободны не все — статус `PARTIAL` / `HIDDEN` по §2c. Для «ИЛИ» (взаимозаменяемые ресурсы одной услуги) достаточно одного свободного.

Эталон для тестов (10:00–20:00, minDur 2 ч, buffer 30, шаг 30, пустой день):
| Длительность | Старты |
|---|---|
| 5 ч | 10:00, 12:30, 14:30, 15:00 |
| 2 ч, FIXED_SESSIONS | 10:00, 12:30, 15:00, 17:30 |
| 2 ч, FLEXIBLE_START | 10:00, 12:30, 13:00, 13:30, 14:00, 14:30, 15:00, 15:30, 17:30, 18:00 |

**Для родителя:** сначала длительность (чипы с ценой из `quoteOffer`), затем список стартов «10:00–15:00» на выбранную дату.

## 2c. Расписание услуги и гибкий показ («почти подходит»)

**Расписание услуги.** В карточке услуги блок «Когда доступна»: «Как у предложения» (по умолчанию) | «Своё расписание» (дни + время). Хранится на ресурсе услуги (`AvailabilityRule` из #526), не на предложении.

**Размещение услуги внутри праздника** — `OfferModuleItem.placement`: `ANY` (по умолчанию: подбираем окно, где исполнитель свободен) | `START` | `END`. Услуга с `stretchesWithOrder` (зал) занимает весь праздник.

**Статус старта** — `getStartTimes` возвращает для каждого старта:
- `FULL` — все выбранные услуги помещаются; для каждой услуги с ресурсом — её интервал внутри праздника (показываем маме «Аниматор 18:00–20:00»);
- `PARTIAL` — основа свободна, но включённая/доп. услуга не помещается целиком: `issues[] = {service, reason, availableMin, neededMin}`; причины: «не работает в пятницу», «работает 12:00–20:00», «до 20:00 — 1 ч вместо 2», «занят»;
- `HIDDEN` — не помещается обязательная услуга (основа) или вне режима работы предложения.

**Правило показа:** `HIDDEN` не показываем; `PARTIAL` показываем всегда (в календаре — жёлтая точка, в списке — «с пометкой»). Ни один фильтр по дате не даёт пустой выдачи, если основа свободна; сортировка FULL → PARTIAL → ближайшее FULL.

**Карточка для родителя при PARTIAL:** жёлтый блок «Почти подходит» с причинами и действиями: «Оставить так» · «Убрать: <услуга> −N BYN» (если услуга можно убрать / по желанию) · «<ближайший FULL-старт> — всё доступно». Кнопка становится «Отправить заявку».

**Бронь по PARTIAL** создаётся как `BookingRequest` со списком `conflicts`; ресурсы без конфликта — `HELD`, конфликтный ресурс не блокируется. Бизнес решает в Календаре. В аналитике бизнеса — отдельный счётчик заявок из PARTIAL.

**Правило стартов для узких окон:** если в окне не помещается второй праздник (`окно < dur + buffer + minDur`), правило «не оставлять непродаваемых окон» не применяется — показываем все старты (иначе 5-часовой праздник в окне 15:00–21:00 не продаётся вовсе).

Эталоны (праздник Пт 15–21, Сб–Вс 10–21; аниматор «можно убрать», 2 ч, своё расписание Сб–Вс 12:00–20:00; зал — основа):
| Старт | Длит. | Статус |
|---|---|---|
| Пт 15:00 | 2 ч | PARTIAL: «Аниматор не работает в пятницу» |
| Сб 10:00 | 2 ч | PARTIAL: «Аниматор работает 12:00–20:00» |
| Сб 12:30 | 2 ч | FULL, аниматор 12:30–14:30 |
| Сб 10:00 | 5 ч | FULL, аниматор 12:00–14:00 (ANY) |
| Сб 19:00 | 2 ч | PARTIAL: «до 20:00 — 1 ч вместо 2» |
| Пт 15:00, аниматор убран | 2 ч | FULL |
| окно 15:00–21:00, 5 ч | — | старты 15:00, 15:30, 16:00 |

## 3. Жизненный цикл удержания мест (решить до `getSlots`)

`BookingRequest` расширяется полями: `sessionId?`, `startsAt?`, `endsAt?`, `seats` (default 1), `holdUntil?`.

**Группы (места):**
- Заявка в статусе `NEW` с `holdUntil > now()` держит места. После `holdUntil` — не держит (ленивое освобождение: учёт по условию, без зависимости от фонового job).
- Занято = сумма `seats` по `CONFIRMED` + `NEW` с `holdUntil > now()`.
- Резерв: транзакция → `SELECT ... FROM "OfferSession" WHERE id = $1 FOR UPDATE` → подсчёт → вставка заявки. Для слотов из правил без строки сеанса — материализовать `OfferSession` при первой брони (upsert по `offerId + startsAt`), затем `FOR UPDATE`.
- Фоновый job раз в N минут переводит просроченные `NEW` в `EXPIRED` (новый статус, если нет) — только для уведомлений и аналитики, не для корректности.
- `holdUntil` по умолчанию: 24 ч или начало сеанса минус `leadTimeHours`, что раньше.

**Эксклюзивные ресурсы (праздники):**
- Резерв = `BookingAllocation` со статусом `HELD` и сроком истечения (проверить, есть ли поле в #526; если нет — добавить в рамках этого ТЗ, согласовав с #529).
- Exclusion constraint не знает про `now()`, поэтому просроченный `HELD` блокирует слот, пока не освобождён. В транзакции резерва перед вставкой: `UPDATE "BookingAllocation" SET status = 'EXPIRED' WHERE "unitId" = $1 AND status = 'HELD' AND "expiresAt" < now()`.
- Интервал allocation включает `bufferMin`.
- Нарушение constraint (`23P01`) → бизнес-ошибка «слот только что заняли», не 500.

**Ресурсы: «И» и «ИЛИ».** Два разных случая, которые нельзя смешивать:

| | Что это | Когда слот доступен | Результат |
|---|---|---|---|
| **«И»** | Разные услуги одного праздника, у каждой свой ресурс (зал + аниматор) | Только если свободны **все** ресурсы всех услуг | Все свободны → `FULL`. Не все → `PARTIAL` (основа свободна) или `HIDDEN` (занята основа) — правила и причины в этом разделе выше |
| **«ИЛИ»** | Взаимозаменяемые ресурсы **одной** услуги (два зала) | Если свободен **хотя бы один** | Слот есть; `unitIds` / `resourceIds` в ответе — список подходящих свободных ресурсов; конкретный ресурс выбирает бизнес при подтверждении заявки |

**Правило пилота относится только к «ИЛИ»:** бизнес вручную выбирает ресурс при подтверждении; автоподбор «любой из двух залов» — следующий этап. Интерфейс `getSlots` / `getStartTimes` возвращает список подходящих ресурсов уже сейчас, чтобы автоподбор не ломал API. Проверка «И» (все ресурсы услуг праздника) — часть фазы 3 и в пилот не откладывается.

## 4. `getSlots`

```ts
getSlots({ offerId, from, to, requestedSeats = 1 }): Promise<Slot[]>

type Slot = {
  startsAt: Date; endsAt: Date;   // UTC
  remainingSeats: number | null;  // null для эксклюзивных
  unitIds: string[];              // подходящие свободные ресурсы
  sessionId?: string;
};
```

Алгоритм:
1. Загрузить `OfferBooking`, режим, тип. `NONE` / `REQUEST_ONLY` / `EXTERNAL` → `[]`.
2. Ограничить окно: `[max(from, now + leadTime), min(to, now + horizon)]`.
3. Построить кандидатов в локальном timezone оффера: из правил (по дням недели), из `OfferSession`, из окон ресурсов + `durationMin` с шагом (15 мин, константа).
4. Вычесть исключения.
5. Эксклюзивные: вычесть активные allocation (HELD не просроченные, CONFIRMED) с учётом буфера; оставить кандидатов, где свободен хотя бы один привязанный ресурс.
6. Места: посчитать занятость по §3, оставить `remaining >= requestedSeats`.
7. Конвертировать в UTC, отсортировать.

`getSlots` **только считает**. Резервирование — отдельная функция `reserveSlot`, повторяет проверку внутри транзакции (§3).

**Время:** локальное время хранится как минуты от полуночи; в UTC переводить через библиотеку с tz-базой (`date-fns-tz` / `Temporal` polyfill — что уже в проекте). Несуществующее локальное время (весенний перевод) — слот пропускается; повторяющееся (осенний) — берётся первое вхождение.

## 6. Тесты

- Обычные интервалы; интервал через полночь.
- DST: `Europe/Warsaw` — последнее воскресенье марта (02:00–03:00 не существует), последнее воскресенье октября (02:00–03:00 дважды). `Europe/Minsk` — без переходов.
- Пересечения allocation, буфер на границах, `[)` (конец = начало следующего — не конфликт).
- Просроченный HELD освобождается в транзакции резерва; просроченный `NEW` не учитывается в местах.
- Вместимость: последний свободный слот — 2 параллельных `reserveSlot` (Promise.all на реальной БД), ровно один успех.
- Конфликт оффера и конструктора праздников на одном `BookingUnit` — второй получает бизнес-ошибку.
- `leadTime` и `horizon` на границах.
- Регрессия: офферы с `NONE` / `REQUEST_ONLY` / `EXTERNAL` после миграции работают как в ТЗ 1.
