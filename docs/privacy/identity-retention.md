# Хранение данных идентификации удалённых аккаунтов (постановление № 850)

## Зачем

Постановление Совета Министров РБ от 23.11.2018 № 850 обязывает владельца
интернет-ресурса хранить сведения, полученные при предварительной
идентификации пользователя (ФИО, номер мобильного телефона и/или email),
на время действия пользовательского соглашения **и в течение года после его
расторжения**, на серверах, физически размещённых на территории Беларуси.

До этого изменения `deleteAccount` стирал телефон и email сразу — требование
о годовом хранении не выполнялось.

> Действующую редакцию постановления (состав сведений, сроки) нужно сверить
> на pravo.by или с юристом. Этот документ описывает техническую реализацию,
> а не юридическое заключение.

## Как устроено

| Шаг | Где | Что происходит |
| --- | --- | --- |
| Удаление аккаунта | `src/server/account/deleteAccount.service.ts` | В той же транзакции, **до** обнуления колонок `User`, сведения (email, телефон, бизнес-телефон, отображаемое имя, Telegram id/username, даты) шифруются и пишутся в `IdentityRetentionRecord`. Ошибка записи откатывает всё удаление |
| Нет ключа | там же | Удаление отклоняется до любых записей: `IDENTITY_RETENTION_UNAVAILABLE` → HTTP 503 с понятным текстом. Fail closed: нельзя потерять данные, которые закон требует хранить |
| Срок | `purgeAfter = agreementEndedAt + 1 календарный год` | 29 февраля → 1 марта, срок никогда не короче года |
| Удаление по сроку | `GET /api/cron/identity-retention-purge` | Ежедневно в `scripts/deploy/run-prod-notification-jobs.sh`; удаляет записи с `purgeAfter <= now`, отдаёт только количество |
| Выдача по запросу | `node dist/ops/identity-retention-disclose.js` | Расшифровка офлайн-ключом, запись в `AdminAuditLog` до вывода данных |

### Шифрование

Гибридная схема: случайный ключ AES-256-GCM на каждую запись (AAD привязывает
шифротекст к `userId`, строки нельзя подменить), ключ данных обёрнут
RSA-OAEP-SHA256 **публичным** ключом. Требование к ключу — RSA не короче 3072 бит.

На сервере лежит **только публичный ключ**: приложение может зашифровать
запись, но не прочитать её. Даже полный доступ к серверу и базе не раскрывает
архив. Приватный ключ хранится офлайн у владельца.

`keyId` — первые 16 hex SHA-256 от публичного ключа (SPKI DER). Он хранится в
записи, поэтому ротация ключа не ломает старые записи: для них нужен старый
приватный ключ, пока не истечёт их срок.

## Настройка ключа (до деплоя, один раз на окружение)

Без ключа удаление аккаунта на окружении вернёт 503. Перед деплоем этого
изменения на DEV и PROD:

```bash
# На своём компьютере, НЕ на сервере
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 \
  -aes-256-cbc -out mamago-identity-retention-private.pem
openssl pkey -in mamago-identity-retention-private.pem -pubout \
  -out mamago-identity-retention-public.pem
base64 -w0 mamago-identity-retention-public.pem   # значение для env
```

1. В env окружения (DEV и PROD отдельно, ключи разные) задать
   `IDENTITY_RETENTION_PUBLIC_KEY` = base64 публичного ключа (принимается
   также PEM с `\n`).
2. Приватный ключ и пароль к нему сохранить офлайн (менеджер паролей +
   резервная копия). **Потеря приватного ключа = невозможность выполнить
   законный запрос** по уже удалённым аккаунтам.
3. Приватный ключ и пароль **никогда не копировать на APP/DB/worker хост, в контейнеры и на облачные CI-runner**, даже временно. Для выдачи используется отдельно защищённая операторская машина с контролируемым сетевым доступом к БД.

## Выдача данных по запросу уполномоченного органа

1. Зарегистрировать письменный запрос (орган, номер, дата, основание, ответственный), подтвердить полномочия и допустимый объём выдачи. Проверить, что запрашиваемый срок хранения ещё не истёк.
2. Использовать **отдельную доверенную операторскую машину**, а не сервер mamaGo, Docker-контейнер или CI. Ключ и пароль остаются на этой машине. Физическое расположение рабочего места, доступ и обработка выгрузки должны соответствовать проверенным юридическим требованиям (BACKLOG-245).
3. На операторской машине использовать проверенную сборку `dist/ops/identity-retention-disclose.js` от зафиксированного релизного SHA. Открыть временное защищённое соединение к PostgreSQL через одобренный VPN/туннель; используемой роли необходимы только `SELECT` по `IdentityRetentionRecord` и `INSERT` в `AdminAuditLog`. Нельзя открывать PostgreSQL в публичный интернет. Не передавать закрытый ключ по SSH в контейнер.
4. Установить `DATABASE_URL` локально с ограниченными правами и ввести пароль ключа без его записи в shell history или аргументы процесса. Пример команды **на операторской машине**:

   ```bash
   read -rs "IDENTITY_RETENTION_PRIVATE_KEY_PASSPHRASE?Пароль закрытого ключа: "
   export IDENTITY_RETENTION_PRIVATE_KEY_PASSPHRASE
   printf '\\n'
   node dist/ops/identity-retention-disclose.js \\
     --request-ref="Запрос № … от …" \\
     --operator="Ответственный сотрудник" \\
     --private-key-file="./mamago-identity-retention-private.pem" \\
     --phone="+375XXXXXXXXX" \\
     --confirm-host="имя_хоста_бд"
   unset IDENTITY_RETENTION_PRIVATE_KEY_PASSPHRASE
   ```

   При локальном туннеле `--confirm-host` не нужен, если `DATABASE_URL` указывает на `localhost`. Для `--user-id` или `--email` использовать ровно один селектор вместо `--phone`.

5. Утилита сначала фиксирует `IDENTITY_RETENTION_DISCLOSED` в `AdminAuditLog`, только затем выводит JSON. Прерванный аудит должен блокировать выдачу. Результат направлять только по защищённой утверждённой процедуре; не сохранять в CI artifacts, логи приложения и общие каталоги.
6. Проверить наличие записи аудита, закрыть доступ к БД и удалить временные выгрузки согласно регламенту. Приватный ключ остаётся в защищённом офлайн-хранилище оператора; его не должно быть на сервере или в логах.

Коды выхода CLI: 0 — найдено, 1 — не найдено, 2 — отказ/неверные аргументы, 3 — ошибка ключа. Истёкшие записи не подлежат выдаче, даже если фоновая очистка задержалась.

Поиск по телефону сравнивает только цифры (формат ввода не важен) и проверяет
и личный, и подтверждённый бизнес-телефон; email сравнивается без учёта регистра.

## Ограничения

- Аккаунты, удалённые **до** этого изменения, восстановить нельзя: их данные
  уже стёрты.
- Данные действующих (неудалённых) аккаунтов хранятся в `User` как раньше;
  их шифрование — отдельный этап (BACKLOG-242).
- Отвязка или смена телефона у **действующего** аккаунта перезаписывает номер
  без истории; нужно ли хранить прежние номера — юридический вопрос (BACKLOG-245, п. 5).
- Физическое размещение серверов и бэкапов в РБ проверяется вне кода (BACKLOG-245).
