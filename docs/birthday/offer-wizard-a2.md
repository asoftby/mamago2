# Birthday Auto Builder — A2: существующий Offer Wizard

Объём: доработка шестишагового визарда от принятого A1 `c5741ab11`. A3/A4/C/D не реализуются. Новых таблиц и миграций нет. PartyOrder, расчёт тарифов, комиссии и серверные правила подтверждения не изменяются.

## Шесть шагов и категории

Сохранены определения `offerWizardV2Steps.ts`: Формат → О предложении → Услуги и цены → Расписание → Условия и контакты → Проверка.

| Сценарий | Категорийные вопросы шага «О предложении» |
| --- | --- |
| Площадка | Где проходит; длительность; ограничения детей; что входит |
| Аниматор | Кто проводит программу; место; длительность; дети; состав услуги |
| Ведущий | Тот же ANIMATOR и `details.performerRole=HOST`; отдельная таксономия не создаётся |
| Шоу | Место; длительность; дети; состав услуги |
| Мастер-класс | Место; длительность; дети; материалы/состав услуги |
| Торт | Самовывоз/доставка; состав заказа; индивидуальные пожелания; возможность прислать фотографии результата |
| Декор | Получение заказа; состав; индивидуальные пожелания; возможность прислать фотографии результата |
| Готовый пакет | Место; длительность; дети; описание; существующие PackageComponent в дополнительных сведениях |

У торта и декора длительность/число детей раскрываются при необходимости; сохранённые ограничения остаются доступны. Существующие ADULT_ONLY/SPECIFIC не скрываются при редактировании возраста. FOOD/PHOTO/PROGRAM/OTHER остаются доступны в прежней таксономии. Интересы используют прежний справочник и остаются необязательными. Переключение категории не очищает скрытые значения. Фотографии клиента в визард не загружаются.

Дополнительные условия и состав раскрываются постепенно. Вопросы используют пользовательские формулировки; внутренние названия режимов цены и моделей в интерфейс не выводятся.

## Сохранение и совместимость

- `mappers.ts`: сохраняет точные границы возраста в месяцах при неизменённом выборе; восстанавливает валюту, интересы, смысл цены и неизвестные ключи party details. Установленное пользователем «не уточнено» у capabilities хранится как null, чтобы прежнее true не воскресало.
- Активная стоимость проверяется целиком: ошибочная строка не преобразуется в ноль. Скрытые неактивные цены не блокируют другой режим. Переключение способа расчёта не удаляет введённые значения из состояния формы.
- EXACT/FROM/ON_REQUEST передаются явно в существующий нормализатор. Незавершённый черновик без числовой цены остаётся UNKNOWN. Числовой legacy RANGE без вариантов сохраняет обе границы при обычном update; для замены нужно явно выбрать другой способ расчёта. Новая ценовая формула не вводится.
- API сохраняет переданную валюту; старые клиенты без валюты при update сохраняют текущую, при create действует прежний BYN. Новые поля необязательны.
- `details-schemas.ts` и `partyWizardInput.ts` проверяют структурированные условия и границы участников на backend, не удаляя неизвестные сохранённые ключи.
- Во время сохранения/отправки основные поля заблокированы, чтобы ответ сервера не перезаписал более поздний ввод.

## Состав пакета

Используется только существующий PackageComponent. Визард редактирует title/category/position; существующие refOfferId, priceSnapshot, priceDelta и isOptional не переписываются. Новые строки используют существующие DB defaults; соответствие removable/isOptional не определяется.

`savePackageComponents` выполняется в транзакции оффера, после ACL, с блокировкой строки Offer и проверкой baseline. Чужие ID, устаревший снимок и удаление позиции, связанной с PartyOrderItem, отклоняются. Переход черновика услуги в пакет проверяет результирующий тип. Опубликованный состав не меняется напрямую до согласования процесса его модерации. Неизменённый состав не отправляется повторно; обычное редактирование legacy-пакета не запускает перепись компонентов.

Legacy includedCategories остаются описанием старых пакетов. Только явное редактирование состава заменяет эту проекцию каноническими строками. После успешного Save очищаются обе legacy-копии формы, поэтому второй Save не возвращает старый состав.

## Расписание и готовность

Переиспользованы PartyResourceSchedule, PartyResourceEditor, API booking-units, существующий BookingUnit и slot-preview. Доступны дни и интервалы, минимальная длительность, шаг начала, подготовка и уборка. При редактировании восстанавливаются прежние значения, включая null; исключения и связи с другими офферами сохраняются. Буферы занимают время и не создают автоматическую доплату.

Ресурсные интервалы сами по себе не включают онлайн-запись. Предпросмотр использует текущий slot engine и сохраняет прежние проверки bookingMode. Существующие тарифы, дополнительные часы и редакторы услуг продолжают работать; нового календаря или механизма бронирования нет.

На шаге проверки разделены:

1. Публикация — существующая валидация и модерация.
2. Участие в конструкторе — последующая проверка условий и допуска компании; optional-данные не превращаются в обязательные.
3. Автоматическое подтверждение — не включается заполнением визарда; текущие серверные проверки сохраняются.

Это объяснение готовности, а не обещание выполнения A3/A4 или успешной доставки заявки.

## Нагрузка и приватность

Редактор получает компоненты в существующем server load и существующем GET, без второго клиентского запроса. Prisma include может добавить один индексный relation-read компонентов; число SQL-запросов отдельно не измерялось. Успешный PATCH возвращает идентификаторы состава вместе с текущим ответом, поэтому повторный save не требует перезагрузки. Состав записывается только после явного изменения, без блокировки/переписи при обычном save. При изменении добавляются lock/read состава и операции по изменённым строкам; лимит новых редактируемых списков — 30 позиций. Запросы ресурсов остаются ленивыми, при раскрытии настройки. Нет polling, новых внешних платных вызовов и межпользовательского кэша.

## Открытые решения

- Каноническое выделение ведущего в общей таксономии и будущая семантика ranking. Сейчас HOST — уточнение существующей категории ANIMATOR, без новой eligibility-логики.
- Изменение состава опубликованного пакета: как модерировать и согласовывать изменения относительно существующих заказов. До решения состав защищён.
- Политика настройки optional/removable, перерасчётов и скидок пакета, приоритетов нескольких источников цены, валютных пересчётов, комиссий, SLA и автоматического подтверждения остаётся в A1 и требует решения владельца.
- Нужен ли бизнесу редактор двух числовых границ legacy RANGE; сейчас обеспечено сохранение прежних данных и явная замена способом расчёта.
- Категорийные продуктовые правила торта/декора (вес, доставка, минимальный заказ и отдельные надбавки) не выдуманы; используются текущие редакторы и ручное согласование.

## Приёмка

Создание/повторное сохранение всех восьми сценариев; смена категории без очистки скрытых данных; ADULT_ONLY и точные месяцы; интересы и валюта; три смысловых режима цены и malformed amounts; legacy RANGE; интервалы/шаг/буферы; канонический состав/двойной save/конкурентность/чужие ID; шесть шагов на мобильном экране; прежние проверки визарда, типов, lint и сборки. Результаты исполнения и независимого ревью находятся в сопровождающем отчёте A2.
