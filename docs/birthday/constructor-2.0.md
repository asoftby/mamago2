# Конструктор праздников mamaGo 2.0 — продуктовый контракт

Статус: утверждён владельцем 10 ноября 2026 как основа разработки. Базовый аудит: `dev` @ `9d630ae10bb0992d73fc90137a31c802bb783ce8` (9 ноября 2026), статическое чтение кода.

Этот документ — источник истины для всех PR конструктора 2.0. Действующие инварианты заявок, цен и подтверждений остаются в `party-confirm-stage2.md`, `business-response-pr5.md`, `package-change-quote.md`; чек-лист выпуска — в `release-gate-2026-10-28.md`. При расхождении с ними побеждают они, а расхождение исправляется здесь отдельным PR.

Намеренное изменение относительно действующего поведения: сейчас контакты родителя бизнесу не раскрываются даже после подтверждения (`party-confirm-stage2.md`, R3). Правило раздела 4.4 вступает в силу только вместе с PR, который его реализует; до этого действует прежнее поведение.

## 1. Главный принцип

Родитель не конструирует праздник самостоятельно — mamaGo предлагает подходящее решение. Свободный выбор остаётся в каталоге, а после оформления родитель управляет единым динамическим сценарием.

Под видом упрощения родителю нельзя снова предлагать самому комплектовать праздник из площадок, аниматоров и дополнительных услуг. Конструктор выполняет одну задачу: предлагает законченный подходящий праздник и помогает организовать его до конца.

## 2. Запреты для всех PR

- Не переписывать работающие механизмы: `PartyOrder`, `PartyOrderItem`, `BookingRequest(kind=PARTY)`, `PartyQuote`, `PartyProviderInvite`, `PartyOutbox`, `BookingUnit` / `BookingAllocation`, Offer Wizard V2, `BookingsInbox`.
- Не создавать вторую систему заявок, второй источник доступности, второй календарь, второй редактор офферов, вторую CRM, вторую систему планирования.
- Расчёт цены, проверка ресурсов и переходы статусов — только на сервере. Сайт, бизнес-кабинет и Telegram Mini App вызывают одни и те же сервисы `src/server/birthday/*`.
- Каждый PR начинается с короткого аудита: что по этой функции уже есть в репозитории и в ветках #1148, #1175, #1178, #1185, что переиспользуется. Отчёт — в описании PR до первого коммита с кодом.
- Новое поведение включается флагом, выключенным по умолчанию. Включение на PROD — отдельное решение владельца, не следствие слияния PR.
- Уведомления — только через `PartyOutbox`. Новых фоновых процессов нет.
- Действуют правила `CLAUDE.md`: одна задача = одна ветка = один PR в `dev`; миграции пишутся вручную.

## 3. Законченный праздник

В выдачу «Подобрать праздник» попадает только законченный праздник. Три критерия:

1. Праздник можно провести без обязательного приобретения других услуг.
2. Программа соответствует возрасту, формату, вместимости и длительности.
3. Известны включённые услуги, правила стоимости и условия проведения.

Главное — самодостаточная программа, а не категория развлечения или число компонентов. Пакет площадки с полноценным мастер-классом — законченный праздник и без аниматора.

Автоматическая проверка (`isCompletePartyOffer`, одно серверное правило для подбора, замены и подсказки бизнесу в визарде) опирается на данные оффера, а не на список разрешённых категорий:

- есть описанная программа и длительность;
- заданы возраст и вместимость;
- перечислено, что входит;
- указан режим цены и условия.

`PARTY_PACKAGE` проходит при выполнении этих условий. `PARTY_SERVICE` проходит, если оформлен как самостоятельная программа в любой подходящей категории и для формата «в заведении» включает место проведения. Технические категории служат автоматической проверке и не должны исключать готовые программы, оформленные бизнесом в другой подходящей категории.

Не проходят предложения, которым для проведения праздника обязательно нужна другая услуга: аренда зала без программы, торт, декор, фото, кейтеринг. Они остаются в каталоге `/[city]/birthday`.

Автоматическая комбинация нескольких независимых исполнителей в релиз 2.0 не входит.

## 4. Сквозной процесс

Бизнес публикует предложение → mamaGo подбирает праздник → родитель отправляет заявку → бизнес отвечает через Telegram → сценарий обновляется.

### 4.1. Бизнес публикует предложение

- Существующий шестишаговый Offer Wizard V2; типы `PARTY_SERVICE` и `PARTY_PACKAGE`. Отдельного редактора праздников нет.
- Доступ бизнеса открывается существующим выключателем `BUSINESS_OFFERS_ENABLED` (переводится из константы в серверный env-флаг). Новых API создания офферов нет.
- Оффер без активного `BookingUnit` с расписанием публикуется в режиме «по подтверждению бизнеса» и не выдаётся за автоматически бронируемый.
- Шаг 6 сообщает бизнесу режим доступности и то, попадёт ли оффер в подбор по разделу 3.

### 4.2. Подбор

- Опрос — не более пяти вопросов: для кого, когда, сколько детей, где, бюджет. Город наследуется из территории. Гость проходит опрос без входа. Переиспользуются шаги `when`, `who`, `format`.
- Подбор выполняется на сервере одним запросом; не более 6 карточек; без запросов на каждую карточку.
- Жёсткие условия: статус публикации, город, формат, возраст на дату праздника, вместимость, раздел 3. Затем ранжирование по интересам, бюджету и сохранённым идеям.
- Доступность до выбора времени: «Есть возможное время» — только если сервер нашёл свободный интервал в этот день; иначе «Уточним у организатора». Слово «свободно» до выбора слота не используется.
- Пустая выдача: подсказать, какой один параметр ослабить, и дать ссылку в каталог. Искусственных карточек и одиночных услуг вместо праздника не показывать.
- Шаг ручного выбора площадки и услуг (`pick`) в основном пути отсутствует.

### 4.3. Заявка

- После «Выбрать праздник» — подтверждение состава, даты, времени из свободных слотов, числа гостей, контакта и цены с её режимом. Конкретный слот проверяется здесь.
- Блока выбора дополнительных услуг в основном пути нет. Платные опции самого пакета показываются внутри его состава.
- Вход требуется только для отправки. Для родителя действие одно.
- Отправленная заявка не равна подтверждённой брони, и интерфейс говорит об этом прямо.

### 4.4. Ответ бизнеса

- Серверная логика ответа, согласования цены и подтверждения с блокировкой ресурса не меняется.
- Telegram Mini App входит в релиз 2.0 как другой интерфейс к тем же заявкам: существующий `BookingsInbox` и те же API. Вход проверяет подпись Telegram токеном бизнес-бота, привязку бизнеса и активное членство; каждое действие дополнительно проверяет роль и принадлежность заявки.
- Веб-кабинет — резервный интерфейс: бизнес без Telegram или при недоступном Mini App выполняет все действия в кабинете.
- Визард и настройка ресурсов в Mini App не открываются.
- Имя и телефон родителя видны подтверждённому исполнителю после `CONFIRMED`, без условия предоплаты, только через сервер с проверкой доступа. Сведения о ребёнке, контакты и внутренние данные заказа в Telegram-уведомления не попадают.

### 4.5. Мой праздник

Один экран `/me/birthdays/[id]`, данные только из единого заказа:

- статус праздника и следующий шаг;
- программа по времени: до отправки — неполная, после отправки — со статусами, после подтверждений — фактический план;
- исполнители со своими статусами; общий статус вычисляется из обязательных частей;
- цена: подтверждённая, предварительная, не оценённая; включённые в пакет компоненты не суммируются повторно;
- идеи;
- вишлист, связанный с этим праздником; модели, публичная страница и брони Wishlist не переписываются;
- замена: при отказе или истечении срока родитель выбирает из законченных вариантов; сценарий, идеи и вишлист сохраняются. Текст статуса — «Нужна замена — выберите вариант».

### 4.6. Мой план

Новая система планирования не создаётся; используется существующий `PlanItem` и `PartyOrder.planItemId`.

- У праздника с установленной датой ровно одна связанная запись в «Моём плане».
- Из «Моего плана» открывается динамический сценарий.
- Изменение даты праздника синхронизирует запись.
- Отмена и перенос корректно отражаются в обоих разделах.
- Повторное сохранение не создаёт дубли.
- Запись не хранит копий программы, цены и статусов; ручная правка плана не меняет связанную запись.

Реализацию сначала искать в #1178 и #1148 и переносить только недостающее.

### 4.7. «В сценарий ДР»

- Второе действие в существующей модалке сохранения, рядом с «В коллекцию».
- Показывается для публикаций с установленной праздничной релевантностью независимо от наличия черновика: праздничные офферы, места с опубликованными праздничными офферами, статьи и подборки журнала с праздничной тематикой. Для нерелевантных публикаций не показывается.
- Если праздник уже существует — предложить его выбрать; если нет — создать одним действием «Новый праздник», без опроса, ребёнка, даты и бюджета.
- Сохранённое попадает в «Идеи» праздника. «Сохранить в сценарий» не означает «Отправить заявку»: `BookingRequest` не создаётся.
- Хранение — отдельная связь `PartyIdea` по образцу `CollectionItem`, со ссылкой на уже существующую сохранённую идею. Повтор в тот же праздник не создаёт дубль.
- Заявку можно отправить только по праздничному офферу; место или статья остаются идеей.
- Неполный черновик никогда не попадает в отправку: `venueMode` может отсутствовать только в статусе `DRAFT` (ограничение на уровне БД).

## 5. Границы релиза 2.0

Входит: короткий подбор законченных праздников, каталог, заявка без сборки, единый сценарий с программой, ценой, идеями, заменой и вишлистом, связь с «Моим планом», «В сценарий ДР», публикация офферов бизнесом через Offer Wizard V2, ресурсы и расписания, согласование и подтверждение, Telegram Mini App поверх `BookingsInbox`, раскрытие контактов после подтверждения.

Не входит (см. `docs/engineering/backlog.md`): автоматические комбинации нескольких исполнителей (BACKLOG-238), авто-волна исполнителей (BACKLOG-239), производственная вместимость тортов, декора и кейтеринга (BACKLOG-240), удаление legacy-демо компонентов карточки праздника (BACKLOG-202). Старый шаг `pick` удаляется отдельной задачей после стабилизации подбора; до этого он остаётся за выключенным флагом подбора.

## 6. Порядок работ

A. Аудит, контракты, демо-данные и флаги — без изменения публичного поведения.
B. Подбор готового праздника: опрос → предложения → заявка.
C. Мой праздник: сценарий, идеи, сохранение, стоимость, замены, вишлист, «Мой план».
D. Бизнес и Telegram: визард, заявки, Mini App, контакты.
E. Интеграционная проверка и релиз: E2E, DEV, миграции, включение флагов, GO в PROD.

Этап A запускается сразу. Этапы B–D разрабатываются изолированно за выключенными флагами и не включаются в релиз без отдельного GO и проверки зависимостей RC1 (#1103). Ветка #1148 целиком не сливается: переносятся только недостающие и совместимые изменения.

Готовность каталога к включению подбора оценивается покрытием типовых запросов родителей — возраст, бюджет, формат, дата, вместимость, — а не числом публикаций.

## 7. Критерий готовности

Сквозной сценарий на изолированных данных и затем на DEV:

бизнес создаёт предложение → заполняет цену и ресурсы → проходит модерацию → родитель находит его через подбор → отправляет заявку без выбора отдельных услуг → бизнес получает её в Telegram и открывает в Mini App → согласовывает цену → подтверждает ресурс → родитель видит подтверждение, программу и запись в «Моём плане» → при отказе выбирает замену.

Отдельно проверяются: сохранение публикации в новый праздник без опроса, повторное открытие черновика, вишлист праздника, отсутствие двойной брони при конкурентных заявках, идемпотентность каждой операции, работа бизнеса без Telegram.

Основные серверные механизмы присутствуют в `dev`; их сквозная работоспособность считается подтверждённой только после прохождения `release-gate-2026-10-28.md` на DEV.
