# Единый контракт данных конструктора праздника

## Статус и границы A1

Контракт для Birthday Auto Builder по Master Spec V2.1 от 5 ноября 2026 и
дополнениям Offer Wizard, слотов, уведомлений и Telegram Business Mini App.
Владелец разрешил только A1. База: `dev@f2d40155667bbc04f2f0fb1bc9556bf708ee3732`.

Результат A1 — карта источников, типизированные структуры и проверки их инвариантов.
Схемы находятся в `src/lib/birthday/constructorContract.ts`; типы выводятся из Zod,
чтобы проверки и TypeScript не расходились. Эти декларации пока не импортируются
рабочими API/сервисами. Нет новых маршрутов, UI, алгоритма сборки, адаптера старых
данных, миграций, отправки уведомлений или изменения существующего поведения.
Прохождение схемы не является доказательством авторизации, публикации, свободного
ресурса, доставки сообщения или согласия родителя.

Сохраняются один шестишаговый Offer Wizard и агрегат `PartyOrder` с его
`PartyOrderItem`. `BirthdayCatalogItem` остаётся публичной проекцией, а не новой
таблицей и не полной моделью для подбора. Новая `PartyScenario` не вводится.

## Типизированные границы

| Структура | Назначение |
| --- | --- |
| `OfferForConstructor` | Серверная проекция оффера с явными неизвестными и версиями источников; не публичный payload |
| `PartySelectionContext` | Версия существующего заказа, FULL/PART, формат, subjects, точный возраст на дату события без DOB, интересы, целевая территория/место, границы бюджета, диапазон дат, необязательный точный интервал, дети/взрослые |
| `ServiceInterval` | UTC-интервал `[startAt,endAt)`, конец строго позже начала |
| `ResourceWindow` | Ресурс, сервисный и занятый интервалы; занятость расширена точно на prep/cleanup |
| `AvailabilityEvidence` | AVAILABLE, PARTIAL, UNAVAILABLE, UNKNOWN; время проверки и конкретный проверенный интервал |
| `PackageComposition` | Структурированные компоненты либо честное legacy-покрытие, без синтетических component ID |
| `PartyProgramItem` | Стабильная позиция, роль, происхождение, pinned, lifecycle, интервал и зависимости |
| `PreliminaryEstimate` | Версия заказа, строки цены, известный минимум, списки неоценённых/неподтверждённых позиций; final=false |
| `BusinessPartyRequestTarget` | Только версия навигационного контракта и ID конкретного BookingRequest |

Идентификаторы и revision в SourceRef — ссылки на реальные источники и их
версии, а не произвольные значения клиента. Для Offer применяется его версия
изменения; для OfferBooking — pricingRevision; для PartyQuote — version. Для
PackageComponent без собственной revision используется версия охватывающего
пакета. Конкретную fingerprint-проекцию адаптер реализует в A3, не в A1.

Денежные значения — строки BYN с двумя десятичными знаками, без float-конверсии
в DTO. Это формат обмена, не новая формула. Числовой расчёт остаётся у существующего
калькулятора в копейках/Decimal. Нулевой EXACT допустим только если явно известен;
ON_REQUEST не имеет amount. UNRESOLVED в строке сметы сохраняет причину конфликта
или отсутствия данных, не маскируя её как намеренный ON_REQUEST. INCLUDED ссылается на родительскую позицию и компонент,
не добавляет повторную сумму. FROM — нижняя граница, не согласованный итог.
Схема сметы проверяет структуру, ссылки и отсутствие циклов включения; она не рассчитывает и не подтверждает
арифметику итога. Расчёт, актуальность и запрет повторной оплаты проверяются в A4.

Неизвестная цена и намеренно опубликованный ON_REQUEST различны. Если исходная
цена противоречива, нельзя выдавать её как точную или бесплатно: сервер помечает
UNRESOLVED, оставляет её на уточнение и сообщает причину. A1 не конвертирует
невалидный persisted payload в допустимый DTO автоматически.

## Ограничения сигналы и неизвестность

| Измерение | Жёсткое правило | Неизвестность / мягкий сигнал |
| --- | --- | --- |
| Публикация и бизнес | Непубличный/недопущенный не участвует | Неизвестность не даёт разрешения на отправку |
| Возраст и участники | Явное нарушение ограничений исключает | Пустая необязательная граница не становится нулём; UNKNOWN не означает запрет |
| Формат и география | Подтверждённое противоречие исключает | Неполные legacy-данные помечаются, не приравниваются к подходящим |
| Доступность | Подтверждённая занятость на требуемый интервал исключает | UNKNOWN/PARTIAL видны; альтернативный интервал не подтверждает исходный |
| Бюджет | Не критерий допуска бизнеса | Мягкий сигнал; 10% допуска из V2.1, превышение не равно согласию |
| Интересы и рейтинг | Не исключают сами по себе | Нет сигнала — нейтрально; Boost не влияет на автоматическую программу |

HARD/UNKNOWN — неизвестный результат проверки жёсткого ограничения, а не HARD/MISMATCH.
Для availability дополнительное мягкое понижение UNKNOWN/PARTIAL относится к
общей ranking foundation и будущему A4; A1 не задаёт веса. Для географии/формата
нельзя ни гарантировать совместимость, ни молча исключать старый оффер только
из-за необязательного пропуска: показать неизвестность, уточнить до отправки.

Известная пустота, неизвестность и неприменимость не смешиваются: например,
NOT_A_PACKAGE явно отделяет услугу от пакета; UNKNOWN zone — не всемирный выезд.
NULL-граница диапазона означает отсутствие заявленной границы. Интервалы timezone
интерпретируются существующим minskBookingWindow; не через timezone браузера.

## Временные интервалы и ресурсы

У каждой позиции свой интервал, у ресурса — расширенная занятость. Формат даты
без времени хранится отдельно от UTC-интервала. Диапазон дат не преобразуется
молча в первый день. Без точного интервала availability=UNKNOWN/NO_EXACT_TIME.
В AVAILABLE windows перечислены проверенные альтернативы ресурсов для одного
и того же полного интервала; это не аллокации и не набор уже выбранных ресурсов.
PARTIAL содержит предложенные интервалы и не разрешает автоматическую замену
времени пользовательской позиции. Порядок зависимостей не определяется одной
линейной программой: независимые услуги могут пересекаться, общий эксклюзивный
ресурс — нет. Циклы зависимостей и конфликты всей программы проверяются в A4.

Шаг начала привязан к расписанию ресурса, prep/cleanup не прибавляются к цене
как оплаченные часы автоматически. Условия аренды/продления требуют решения
владельца. Подтверждение всегда повторно проверяет бизнес, оффер, ресурс,
занятость и ограничения в существующей транзакции, а не доверяет preview.

## Передача конкретной заявки в Telegram Business

`BusinessPartyRequestTarget` содержит только `requestId` и версию. Он означает
«открыть эту заявку», не «подтвердить». Ссылка не содержит businessId, контактов,
имени ребёнка, токенов сессии или подписанных ссылок файлов и не даёт доступа.
Конкретный URL и открытие существующего inbox/detail реализуются в D.

Для сайта и Mini App одна цепочка: серверная business-авторизация → чтение своей
заявки → действующая версия → существующие respond/confirm/resolve/prepaid
сервисы. Mini App проверяет подпись актуального Business Bot, окружение,
BusinessTelegramConnection и активное членство OWNER/MANAGER. Нельзя принимать
заявленную клиентом роль/бота, использовать family connection как business identity
или делать downgrade в семейного бота при сбое. Переиспользуются криптографические
и session-примитивы, а не копируется booking-логика.

До «Цена согласована» бизнес получает только brief своей позиции из V2.1 §11.
После неё имя и контакты выдаются только выбранному исполнителю; остальные
позиции/семейный профиль не выдаются никогда. Референсы запрашиваются заново
через ACL позиции и короткий TTL; ID в ссылке и прежняя роль не достаточны.
Файловый доступ и текст пожеланий не должны обходить этот privacy-контракт.

Доставка остаётся PartyOutbox → Notification → NotificationDelivery → Business Bot.
Проверяются BUSINESS_BOOKINGS_INBOX_UI, TELEGRAM_BUSINESS_DELIVERY_ENABLED,
PARTY_CONFIRMATION_ENABLED. Существующий callback подтверждения сохраняет свою
подпись/версию/проверку ресурса и не подменяется навигационной ссылкой.
Неоднозначная попытка доставки требует reconciliation, не слепого повтора.
SLA не переносится на момент доставки без отдельного продуктового решения.

## Совместимость и внедрение после A1

1. A2 сохраняет шесть шагов и расширяет текущие редакторы, не делает схемы A1
   обязательным payload старого business API. Публикация, участие в подборе и
   готовность быстрого подтверждения — разные результаты.
2. A3 адаптирует существующие Offer/PackageComponent/BookingUnit в контракт.
   Legacy-поля сохраняются; удаление или backfill с догадками не допускаются.
   Конфликт источников виден явно; isOptional не превращается автоматически в
   removable. Для included старых заказов без component ID требуется явная
   legacy-проекция до миграции, не применение новой схемы напрямую к строкам БД.
3. A4 использует один pricing-путь и одну recommendation foundation. DTO не
   заменяет модели и не попадает целиком в публичный каталог или общий кеш.
   Пакетные чтения, ограниченная выборка и проверка query count/p95 обязательны;
   A1 не добавляет DB/API запросов и не заявляет ускорение.
4. D подключает контракты к lifecycle и Telegram. Старый CONFIRMED не переименовывать
   автоматически в финальную бронь. Статус ресурса, согласие цены и выполнение
   условий брони сохраняются как разные факты. Текущие STANDARD/party-заявки
   и DB constraints остаются действующими.
5. C использует существующую Media с приватным lifecycle. Возможность бизнеса
   принимать индивидуальные запросы не равна опубликованным пользовательским фото.

Нет миграции/feature flag A1: модуль пока не участвует в production-пути. Откат —
удаление деклараций/тестов/документа и тестовой команды; данные не менялись.

## Проверка A1 и последующая приёмка

`pnpm test:birthday-contract` выполняет поведенческие проверки схем: legacy/UNKNOWN,
возраст, справочник интересов, денежная точность, конфликт источников, пакет,
интервалы/буферы, мягкие сигналы, взрослый без детей, строки сметы и безопасный
навигационный envelope. Команда включена в существующий test:birthday-catalog.
TypeScript проверяет также fixtures через `satisfies`; lint — изменённые TS-файлы.

Не считать этими тестами доказанными UI, pricing-арифметику, ACL, конкурентность,
доставку или Telegram auth. Полный будущий integration путь: Wizard → сохранение
и повторное открытие → публикация → доступность → сборка → серверная смета →
заявка → канал доставки → ответ → подтверждение ресурса. Дополнительно: все
категории/mobile, недопущенный бизнес, отказ/таймаут, retry, изменённая цена,
PARTIAL, конфликт слота, приватные фото, чужой бизнес/отозванная роль, неизменность
USER/pinned, отсутствие двойной оплаты и сторно. DEV требует runtime SHA,
миграций/флагов и фактической доставки тестовой заявки; A1 этого не выполняет.
